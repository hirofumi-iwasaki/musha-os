# musha-os開発スレッド向け実装指示

- 指示書版：3.0（文書版。OS／外部ABI版とは別）
- 更新日：2026-10-13
- 対応方針書：`docs/boot-readiness-policy.md` 文書版3.0
- 旧版との関係：2.0の起動分離・API／ABI／SDK・A～D工程を維持し、iBCS非採用と具体的ABI候補・検査指示を加えた置換版。

このファイルを、開発を継続しているmusha-osスレッドに渡してください。以下を所有者からの実装依頼として使用します。方針の説明やファイル保存だけで終わらず、指定した直近範囲の文書・コード・試験を進めてください。

---

Musha-OSの「OS初期化」「診断記録」「画面表示」を分離し、その境界を今後のAPI・ABI・SDKへ接続してください。添付の`docs/boot-readiness-policy.md`は旧版2.0を更新した統合方針3.0です。現在のローカル開発を維持して反映してください。

長期方針は、**単一のアプリをRing 3で実行し、主導権をアプリへ渡す。OSは基本I/Oと保護を担当し、アプリの内部構造、mainループ、専有RAM内の管理、GUI等には関与しない**ことです。`step()`や定期的な`musha_poll()`を、最終的な公開SDKの義務にしないでください。

## 1. 今回の実行範囲

対象は`~/Github/musha-os`です。作業開始時のAGENTS.md等、ブランチ、HEAD、未コミット変更、並行作業を調べてください。

**まずA（起動と表示の分離）＋B（API・ABI仕様とSDKの土台）を実装・検証してください。** C（外部Ring 3 Hello）とD（実用I/OとSDK）は後続工程として、依存関係・未確定事項・試験をファイル化してください。C・Dの完成を待たないとAを完了できない進め方にしないでください。

既にA～D相当の機能を実装中または実装済みなら、実際の差分と試験を確認して再利用してください。完成済みのものを古い設計へ戻したり、同じ機能を別系統で重複実装したりしないでください。

今回はローカルの文書・ソース・試験・必要なCI定義の編集、通常ビルド、ホスト／QEMU検証までです。この依頼だけでは次を行わないでください。

- commit、push、タグの作成・変更、Releaseの作成・公開・変更、GitHub設定変更。
- 実USBへの書込み・再フォーマット、物理ディスク操作、OSの再起動。
- 配布確定済みのMI68 PDF、展示用A4紙、公開済みバイナリーの差し替え。
- 自動的なcheckout、reset、clean、stash、rebase、無関係の作業中断・変更削除。

同じファイルへ別の作業主体が書いている場合は変更を直列化し、競合箇所だけ確認してください。独立して進められる試験・文書整理は進めて構いません。変更・実行に必要な権限が足りない場合は、その範囲を明記してください。

## 4. A1：診断記録と描画の責任を分離

記録更新から`render()`が毎回呼ばれる経路を分離し、記録関数はRAM上の状態・イベント更新だけを行うようにしてください。`hide()`で見えなくするだけでは完了ではありません。

記録は上限付きとし、満杯でも初期化を止めないでください。欠落数、直近の重大障害、最初に失敗した段階を残してください。高頻度経路は段階ID・数値を優先し、詳細整形を表示側へ移してください。重複更新によるdirty設定・再描画も抑制してください。

描画は安全な実行点から明示的に呼び、複数更新をまとめ、必要な行・領域だけを反映してください。通常起動の全パネル反復クリアや、自動ページ送りの8秒待ち等は除いてください。

フレームバッファの取得・検査・マッピング、致命的障害の最小表示は保持してください。ビューアー／アプリが描いている画面を、通常の診断側が無断で上書きしないようにしてください。独立したCPU・OSスレッドや割り込み再入を、この分離だけのために追加しないでください。

## 5. A2：I/OをOSランタイムの所有物にする

`app::run()`や`xhci::diagnose()`等に一体化している初期化・継続処理・停止の実際の寿命を調べて、OSサービスの所有者へ移してください。初期化関数が戻ってDropされた機器を、利用可能として公開しないでください。

アプリのハンドル、診断レコード、OSサービス、コントローラー、DMAメモリを区別してください。診断ビューを開閉するだけで、USBリセット・NIC停止・再列挙・マウント解除を行わないでください。

以下は必ず維持してください。

- 複数xHCI、ハブ、入力元選択、キー解放、FIFO回復、切断時の状態整合。
- FAT32/exFAT、ファイル一覧・選択・内容表示、逐次読み出し、別コントローラーのストレージ保持。
- 取消し・期限切れ・途中切断・アプリ障害時の要求番号／世代の検査と安全な回収。
- DMA完了／停止確認前にバッファを再利用しないこと。停止不明なら安全側で保持・停止すること。
- 現行の直列実行や割り込み禁止等の安全前提。変更するなら独立した設計と試験を先に用意すること。

アプリ終了時のハンドル解放と、サービス全体の停止、OS終了を別にしてください。現行公開版がアプリ終了後に停止する契約なら、多アプリOSへ勝手に広げず、その契約を明示して維持してよいです。

## 6. A3：Readyを実状態として実装

型を持つ状態管理とし、画面文字列を状態の情報源にしないでください。

- CORE_READY：CPU・メモリ等の基盤成立。
- OS_READY：起動プロファイルで必須のサービスが実APIから利用可能で、アプリへ移行できる。
- APP_ENTERING：アプリへ実行を渡す直前の記録。
- APP_RUNNING：アプリの実行に到達。初回画面完成とは別。
- APP_LAUNCH_FAILED／APP_EXITED／APP_FAILED、サービス切断・停止、診断表示状態は独立させる。

従来の早い`RUNTIME READY`を意味に合わせて整理してください。`AppEvent::Ready`がコントローラー単位の通知なのかOS全体の準備なのかも区別してください。

必須／任意サービスを明記し、必須失敗でReadyにしないでください。任意LAN不在等は期限付きで理由を残してください。アプリ固有ファイルの内容検査や、RAM反復試験の終了をReadyの条件にしないでください。ただし安全なメモリ検査、機器資源検査、所有権取得、必要なリセット待ちは省略しないでください。

静的リンク・協調実行の移行プロファイルでもAは完了できます。そのReadyは内部APIで検証し、Ring 3／外部SDK／アプリ非依存I/O対応とは表示しないでください。将来の外部アプリはOS_READY後にELF・ABI・必要機能・権限等を照合し、起動不能ならアプリ起動失敗として記録してください。

## 7. A4：計測と公開できる状態

EFI入口、CORE_READY、OS_READY、app_entry、first_frame_completeを分けてください。app_entryは移行直前のOS側時刻と定義し、ユーザー空間実行の実到達証拠とは区別してください。

Readyと時刻を内部で確定してから表示してください。起動後の診断閲覧で時刻を上書きしないでください。未取得の早期時刻をゼロにしたり、別時計を校正せず差し引いたりしないでください。PMタイマー等のラップ、単位・分解能・起点も記録してください。

初回描画は、アプリが要求した最初の画面反映のソフトウェア上の完了です。ディスプレイへの実表示や垂直同期の保証ではなく、OSの進捗文字表示も含めません。画面を描かないアプリを失敗にしないでください。

将来の起動レポートAPIで返す項目を整理してください。内部Panel／BootInfoや物理アドレスを公開せず、版付きの値・上限付きレコードを返す形とします。レポートの読取り自体は描画・サービス再初期化を起こさない契約にしてください。

## 8. B1：API・ABI・SDKの責任をファイルへ落とす

次の3層を区別してください。

**API**：ログ・終了・機能照会・時刻／wait・入力・表示・ファイル・通信の操作意味。エラー、部分完了、EOF、上限、所有権、期限・取消しを含む。

**ABI**：ELF／起動情報、CPU条件、通常のSystem V AMD64を基礎とするC ABI、システムコール境界を別々に定義。固定幅型、サイズ・オフセット・アラインメント、互換性を決める。

**SDK**：Cヘッダー＋libmusha、Rustのmusha-sys＋musha、crt0、sysroot、Clang／LLD／Cargo設定、サンプル、ABI／ELF検査とQEMU支援。

内部のコールバック契約・Rust型・`API_VERSION=5`を、そのまま外部ABIへ公開しないでください。既存サービスを背後で再利用し、検査・変換層を設けてください。

まず公開範囲を最小にし、未提供機能は明示してください。ネットワーク、書込み、POSIX等をヘッダーへ加えただけで対応済みにしないでください。外部アプリへカーネル関数ポインターを渡す設計にはしないでください。

## 9. B2：今回のABI詳細を実装可能な契約にする

**iBCS／iBCS2は採用しません。System V AMD64を基礎とするC ABI、静的ELF64、Musha-OS独自の起動・システムコールABIを組み合わせます。** ELFやレジスター配置を一部共有することを、Linuxバイナリー互換やPOSIX全面対応と説明しないでください。

添付方針書の**第12節をABI詳細の参照元**としてください。同等の`application-abi.md`があればそこへ統合し、レジスターや構造体の別仕様を複数箇所で手修正し続けないようにしてください。数値・配置案は未公開の推奨案です。先行実装が違う場合は理由・既存利用・互換性を調べて調整し、黙って破壊しないでください。

### 9.1 標準との境界と確定台帳

次を区別し、各項目を「採用方針／experimentalな候補値／実装済み／実行検証済み／公開互換性固定」で管理してください。

- 通常C ABI：SysV AMD64／LP64、通常の関数・FFI・型配置。
- 起動ABI：ELF、NOTE、CPU条件、Ring 3入口、RSP／RDI、起動情報、crt0、終了。
- syscall ABI：SYSCALLの番号・引数・結果・保存状態・安全な復帰。
- 既存カーネル：efiapi／Win64等の既存ABIを維持し、必要な橋渡しを定義する。

方針書第12.10節の台帳を作り、syscall番号、エラー数値、NOTE形式、CPUプロファイルID、ABI値、仮想配置と各上限を決めてください。番号はまだ指定されていません。Linuxの番号を当然の値として採用したり、文書版3.0を外部ABI3.0として設定したりしないでください。

### 9.2 C／Rustの公開型と起動情報

型・定数・番号は一つの定義元から生成するか、機械的な整合試験を必須にしてください。公開対象だけを生成し、内部Rust型を丸ごとexportしないでください。

64byteの`musha_start_info_v1`案を検討してください。方針書に全fieldとoffsetを載せています。C／Rustでsizeof=64、alignof=8、全offset、固定幅整数、予約欄を検査してください。v1は構造体案の名前で、ABI1.0公開の宣言ではありません。

起動情報はOSが作るユーザー読出し専用コピーとし、OS内部BootInfoへの参照を渡さないでください。Arena／stackのアドレスはユーザー仮想アドレス、stack_bytesにはguardを含めず、boot_report_handleの0は利用不能の案です。全ページの寿命・初期化・非重複を定義してください。

input長とoutput容量、未知flags、ゼロでないreserved、長い／短いレコード、padding初期化、ハンドルの種類／所有者／権限／世代を定義してください。ホスト上のstruct一致はRing 3実行や安全なコピーの証拠ではありません。

### 9.3 ELFと最初の命令

初期候補をELFCLASS64／ELFDATA2LSB／EM_X86_64／静的ET_EXECとして仕様化し、PT_LOAD、BSSゼロ化、offset／align、範囲・重複・ページ単位W^X、入口とstack／Arenaの非重複を検査する設計にしてください。PT_INTERP、PT_DYNAMIC、PT_TLS等の未対応要素は明示して拒否してください。デバッグセクションや静的リンクで解決済みの情報まで一律拒否しないでください。

NOTEの識別・版・必要機能・要求権限・CPU・RAM／stack量の符号化を固定し、重複・欠落・不一致を拒否する規則を作ってください。NOTEはアプリの安全性や権限許可の証明ではありません。app-checkを付けてもOS側検査を省かないでください。

`_start`はOSが通常callしたC関数ではありません。候補は`RSP % 16 = 0`、RDI=起動情報、CPL=3。crt0が通常callしたC関数入口では`RSP % 16 = 8`です。引数レジスター、フラグ、未指定GPR、FS／GSとFPUの初期状態、戻り先がないこと、main終了から終了syscallまでを定義してください。

APP_ENTERINGを記録しただけでAPP_RUNNING成功としないでください。最初のユーザー側照会syscall等で実到達を確認する試験を設計し、OS_READYや初回画面とは別の節目にしてください。

### 9.4 syscallレジスターとC wrapper

推奨候補はSYSCALL入口、初期の復帰はIRETQです。引数はRAX=番号、RDI／RSI／RDX／R10／R8／R9。結果はRAX=状態、RDX=主結果の独自規約案です。状態はint32_t範囲の値を64bitに符号拡張し、成功0、エラー負値、エラー時RDX=0を候補にしてください。

RAX／RDX／RCX／R11とflagsの扱い、保存GPR、対応するFPU／SIMDを方針書第12.6節と一致させてください。RDXを入力と出力の両方として扱い、Cの第4引数RCXからR10への変換、インラインasm等の破壊・メモリ副作用指定を検査してください。raw syscallの保存規約とSDK関数全体のSysV C保存規約を混同しないでください。

数値未定の段階はasm wrapperの形・コンパイル試験まででよく、ダミー番号を正式ABIと説明しないでください。未知呼出しや未提供機能を成功stubにしないでください。RAX／RDXの受け渡しをホストで模擬した試験は、ゲストの特権移行試験とは別に報告してください。

### 9.5 カーネル入口・復帰の設計レビュー

SYSCALLはRSPを自動変更しないため、TSSのRSP0を設定するだけでは不十分です。ユーザーRSP退避、カーネルstack切替、必要な状態保存を、通常のRust/C関数プロローグより前に行える設計にしてください。

MSR／selectors、入口マッピング、フラグマスク、NMI／例外／再入、TSS／IST、復帰先RIP／RSPとCS／SS、IOPL等を設計してください。既存Win64関数への橋渡しではshadow spaceと整列を確認してください。CPU仕様の参照版とIntel／AMDの検証範囲を記録してください。参考Linuxソースを無条件に取り込む指示ではありません。

C工程の権限移行を、Aの小さな描画修正へ紛れ込ませないでください。Bでは仕様・検査設計・必要な雛形までを整え、実装していない安全な復帰や割り込み処理を完成扱いにしないでください。

### 9.6 CPU・FP・Rustターゲット

初期推奨は基本x64＋SSE2・LP64・no-red-zoneで、AVX以降は既定にしません。CとRust、core／補助ライブラリまで同じプロファイルとし、`-march=native`を避けてください。FPU／SIMDを使わないカーネルの条件と、アプリが使う条件を分離してください。

**Rustのx86_64-unknown-noneはSoftfloat ABIを含む実装があるので、Clangの通常SysV float／double ABIと無条件に同じとは扱わないでください。** 固定するtoolchainのtarget specを確認し、必要ならユーザー用custom targetとcore／alloc再ビルドを用意してください。target-feature変更だけで整合したことにしないでください。

custom target／build-stdの不安定性、nightlyとrust-src等の条件をSDK側へ明示し、既存カーネルのtoolchainを一括で変えないでください。FP引数を公開syscallに使わなくても、通常C↔Rust呼出し、memcpy、最適化、割り込み前後のXMM／x87／MXCSR等を検査する必要があります。整数HelloだけでFP対応を宣言しないでください。

### 9.7 Bの成果物と、C／Dへ残すもの

Bでは公開型、エラー・番号台帳、ELF／起動／syscall規約、SDKターゲット条件、整合試験を成果物にしてください。採番等を行った場合はexperimentalなリビジョンとして記録し、公開ABI固定とは分けてください。

Cには、実CPL=3、CとRustのELF差し替え、正常終了、不正ELF／ポインター／復帰先の拒否、スタック整列、保存レジスターとFP状態のゲスト試験を残してください。Dには、アプリがAPIを呼ばない間のI/O進行、待機・取消し・切断・DMA寿命を残してください。


## 10. B3：Clang／Rust SDKの土台

既存のClang／LLVM・LLD・Cargoを使う構成にしてください。独自コンパイラーフォークやMusha-OS上でのコンパイルは必須にしません。

`sysroot/include/musha/`、`sysroot/lib/`、crt0、libmusha、Rustの低レベル／安全wrapper、ELFリンク設定、CMake toolchain、Cargo設定、サンプル、検査ツールの責任と依存関係をファイル化し、可能な雛形・コンパイル検査を用意してください。既存の同等資産があれば統合してください。

Clangの実ターゲット、sysroot、インクルード／ライブラリパス、使用リンカーを明記し、生成形式と未解決依存を検査してください。ホストmacOS／Linuxのlibcやcrtを混入させないでください。`-ffreestanding`だけで標準ライブラリがそろうとは扱わず、memcpy等とcompiler-rt等の供給方法を決めてください。

Rustはno_stdを基本に、alloc・allocator・async executor・GUIは任意とします。musha-sysにunsafeな境界を集め、mushaで所有権とエラーを包む計画にしてください。

第9.6節に従い、固定したRust targetのSoftfloat条件、Clangの通常SysV条件、core／alloc／補助ライブラリを照合してください。custom targetが必要ならSDKで固定したtoolchainと手順を用意し、カーネル側への一括変更は避けてください。浮動小数点・SIMD・red zone・TLS・unwindの対応範囲を文書化してください。

CRT／syscallラッパー／リンカースクリプトを、候補ABIの64byte起動情報、_start整列、RAX／RDX結果、NOTEと一致させてください。A＋Bでゲスト実行まで未着手なら、それを使えるSDKとして配布しないでください。

Bの時点でゲストローダーやsyscallがなければ、C／Rustの公開型コンパイルやSDKビルド雛形までを実行し、hello.elfのゲスト実行は未実施と明示してください。生成できないコマンドを、READMEの完成済み手順として掲載しないでください。

## 11. C・Dの後続設計を残す

A＋Bの完了時に、次の順序・依存関係・合格条件を記録してください。現在のv0.2.0等の公開条件に自動追加せず、別工程として扱います。

### C：Clang／Rustの外部HelloをRing 3で実行

第9節と方針書第12節で整えたexperimentalな契約を基に、静的ELF64、ユーザー仮想領域、保護されたスタック／Arena、版付き起動情報、最小syscall（照会・ログ・終了）、crt0を実装する工程です。OS用EFIとアプリ用ELF、UEFI用呼出しとアプリC ABI、syscall規約を分けます。Cの実装自体は今回のA＋Bから自動的に開始せず、後続指示または既存の承認範囲に従ってください。

ELF境界、PT_LOAD、W^X、BSS、入口、未対応動的依存／TLS／再配置を検査します。必要機能・権限・CPU条件が合わなければロードを拒否します。ホストapp-checkも同じ規則を試せる構成にしますが、ローダーの検査は省きません。

**同じOSバイナリーで、独立してビルドしたCとRustのhello.elfを差し替えて起動・終了できること**をゲートとします。OSファイルのハッシュ不変、実CPL、_start／main整列、起動情報、BSS、保護属性、無効syscall・ポインター・復帰先、正常な復帰と終了を確認します。

C→Rust／Rust→Cのfloat／double、混合構造体、スタック引数も確認してください。raw syscallはRDXの入力と出力を違う値で検査し、GPR／x87／XMM／MXCSR等の保持を、通常syscallと非同期割り込みの両経路で試験してください。ホストコンパイルの成功だけでは代用しないでください。

### D：実用I/Oとアプリの主導権

表示はRAM上の描画バッファからまとめてpresentし、フォントやGUIをカーネルへ押し込まない方針です。入力・ファイル・対応通信を検査付きAPIへ順次接続します。

OS側は要求／完了／取消し／waitを管理し、SDKは同期・イベント型・任意のasyncを提供します。生のアプリポインターを関数終了後のDMA先へ使い回さず、まずOS所有の有界バッファを使います。Future破棄とDMA完了／回収は分けてください。

アプリがAPIを呼ばない長い計算をしても、必要なI/O・タイマーが進むことを確認します。waitをOSの進行のための周期呼出しにせず、通知の取り逃がし・取消し競合も試験します。内部サービスへの割り込み再入、カーネルスタック・FPU状態を設計し、Ring 3だけで完了としないでください。

## 12. 直近A＋Bの試験

1. 記録更新だけでは描画が発生せず、重複更新でも不要な描画をしない。
2. CORE_READY → OS_READY → app_entryの順序、Ready一回性、起動プロファイルを検査する。
3. 必須失敗ではReadyなし、任意機器不在では定義した制限付き進行。Ready直後に必須APIを使用する。
4. 初期化関数から戻ってもI/O所有者が生存し、診断の開閉では機器やファイルサービスを止めない。
5. 診断OFF／概要／詳細で、同一構成の機能とエラー安全性を保つ。表示の遅さを初期化の同期に使わない。
6. ログ満杯、小画面、描画遅延、未計測時刻、初期化失敗で正しい状態と理由を残す。
7. USB・入力・FAT32/exFAT・逐次I/O・取消し・途中切断・timeout・通信の既存回帰を維持する。
8. C／Rustの公開データ配置、定数、型幅、未知値、上限を検査する。64byte起動情報案は全offsetを検査し、target用objectとホストの結果を区別する。
9. SDK雛形の独立ビルド、ターゲット条件、ホスト依存混入、生成物再生成、ライセンス表示を確認する。
10. 通常版EFI自体をQEMUで確認し、debug／故障注入／probe版と混ぜない。
11. ABI台帳、通常C／起動／syscallの区別、RDX入出力・R10変換・符号拡張・スタック整列を、仕様と生成wrapperの両側で検査する。
12. ClangとRustのFP ABIを比較できる試験素材を用意し、未解消のSoftfloat／SysV差、未実行のゲスト保存・復帰試験を明記する。

時計や描画回数の計測区間を記録し、条件間で同じ時間値になることを要求しないでください。タイミング依存のセクター数ではなく、取消し状態・内容・ライフサイクルを検査してください。期待値や失敗検査を削るだけで合格にしないでください。

実機がない場合、実機確認のみを未実施として残し、独立した実装・ホスト／QEMU検証は進めてください。次に試す通常版ファイルと実機試験票まで準備できますが、実USB更新はこの依頼では行わないでください。
