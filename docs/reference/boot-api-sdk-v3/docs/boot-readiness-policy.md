# Musha-OS 起動完了・初期化・診断表示の分離方針

## API・ABI・SDK分離と、x64 ABI詳細案を含む統合方針

- 文書版：3.0（旧2.0を更新・置換。OS版・外部ABI版とは別）
- 初版作成日：2026-10-12
- 更新日：2026-10-13
- 状態：所有者の更新依頼に基づく統合方針。第12節で採用方針・推奨プロファイル案・未確定値を区別する。実装・検証・公開ABI固定の完了を表明するものではない。
- 想定配置先：`docs/boot-readiness-policy.md`
- 対象：現在のMusha-OSへの段階的な構造改善。特定の過去コミットへ戻す指示ではない。

**今回の追加：iBCS非採用を明示し、SysV AMD64の通常C ABI、静的ELF64・Ring 3起動ABI、Musha-OS独自syscall ABIを詳細化する。64byte起動情報、レジスター・スタック条件、FPU／SIMD、Clang／Rustターゲットと互換性試験を第12節へ追加した。起動分離とSDKの土台（A＋B）を先行し、Ring 3実行と実用I/O（C＋D）は後続とする方針は維持する。**

本資料は日本語の作業用統合案。リポジトリへ反映する際は、既存の英語先行・日本語併記等の規約に従い、同じ意味で統合する。

## 1. 目的と決定

> **OSの起動完了は、起動構成で必須とするサービスが利用可能になり、アプリへ実行を渡せる状態が成立した時点とする。診断画面を描き終えた時点ではない。**
>
> **初期化、状態・診断情報の記録、診断の表示を分離する。OSが起動に必要な準備を終えた後、画面づくりや診断情報の閲覧はアプリ側へ委ねる。**

利用者が「OSはもう起動したのか、それともまだ初期化中なのか」を判断できるようにする。診断のページ送りや大量の再描画を、起動完了待ちに含めない。

単にReadyの文字列を先に表示する、診断表示を隠す、測定区間を短く見せるだけでは、本方針を実装したことにならない。

## 2. 既存ポリシーとの関係

Musha-OSの長期方針は、単一アプリをRing 3で実行し、アプリの内側には原則として関与せず、基本I/Oと保護をOSが提供することである。

本変更は、そのための所有権と責任範囲を整理する。Ring 3、外部ELFローダー、割り込み駆動、プリエンプションの完成を待たずに着手する。これらを一度に実装することも要求しない。ただし公開APIの設計はこの段階から行い、後で診断アプリの内部型をそのままABIへ固定する事態を避ける。

移行中は既存の静的リンク・協調実行を維持してよい。ただし、それを最終的な公開アプリの必須契約とはせず、Ring 3やアプリから独立したI/O進行が実装済みであるとも表示しない。実装中の実行モデルにおいて提供できるサービスを、Ready判定の対象とする。状態情報には実行プロファイル（移行期の静的リンク・協調実行／将来の外部Ring 3等）を区別して記録する。既存の内部API版と、新しい外部ABI版は独立に管理する。

## 3. 起動状態と、アプリ・診断の状態

起動状態を文字列や画面表示から推定せず、型を持つ内部状態として管理する。名称は既存規約に合わせられるが、次の意味を維持する。

| 起動上の節目 | 成立条件 | この状態だけでは約束しないこと |
|---|---|---|
| `CORE_READY` | UEFIから独立するためのCPU・例外処理・スタック・メモリ保護等の基盤が成立 | USB、ファイル、通信などの利用可能性 |
| `OS_READY` | 下記のReady契約を満たし、アプリを開始できる | アプリの初期化完了、最初の画面、任意機器の全面対応 |
| `APP_ENTERING` | 対象アプリへ実行を渡す直前を記録 | Ring 3実行への到達成功 |
| `APP_RUNNING` | アプリ実行への到達が確認された | アプリの処理結果や初回描画の完了 |

実装上は、起動状態、現在のサービス状態、アプリ状態、診断表示状態を分ける。例えば以下のように扱う。

- 起動履歴：開始 → CORE_READY → OS_READY。途中の必須機能失敗はBOOT_FAILED。
- アプリ：未開始 → 実行中 → 正常終了、または異常終了。
- サービス：利用可能、未接続、未対応、失敗、停止等。
- 診断画面：非表示、概要表示、詳細表示等。

`APP COMPLETE`や診断ページの巡回完了は、OS起動完了の条件にしない。起動後の機器切断では、過去のOS_READY到達時刻を変更せず、現在のサービス状態を更新する。サービス停止後に、過去のReadyを現在の稼働状態と誤表示しない。

### 3.1 OS_READYの契約

OS_READYを一度だけ確定する前に、少なくとも次を満たす。

1. 実行、メモリ、例外処理、および提供サービスに必要な時計が準備されている。
2. 起動構成で必須としたサービスが、実際のAPIから利用可能である。
3. 任意機能の未接続・未対応・失敗を記録し、それらを成功と取り違えていない。
4. I/Oの状態と資源が、初期化関数の終了や画面の切り替えで失効しない。
5. アプリを開始する経路と、開始・失敗時に必要なOS側の資源管理が成立している。

起動構成ごとに「必須」と「任意」を明示する。当初は既存の起動アプリに対応する固定の構成でよく、新たな設定ファイル形式や汎用依存関係エンジンは必須にしない。

例：ファイルを利用しない診断構成はストレージなしでも成立し得る。ファイルブラウザーが要求する構成では、必要な読出しサービスを実際に利用できることを確認する。アプリ固有の対象ファイルの有無、内容表示の成功などは、OSサービスの準備と別に扱う。ネットワークが任意なら、LANケーブル未接続でOS全体を無期限に待たせない。

必須機能の失敗を、単なる時間切れや表示上の都合でOS_READYに変換しない。任意機能は期限付きで成否を確定させる。利用可能な機能だけを明示して起動する場合は、その制限を状態情報へ残す。

### 3.2 アプリ読み込みとの境界

現在の静的リンク構成では、OS_READY確定後にアプリの最初のinit／entryへ進む。

将来の外部アプリ構成では、OSのローダーと必要サービスが利用可能な時点をOS_READYとし、その後のアプリ読み込み・検証・配置を別区間として測定してよい。必須のOS初期化をアプリ読み込みの中へ隠してはならない。アプリイメージ破損は、OSの初期化失敗とは区別する。

OS_READYは「この起動プロファイルのサービスが準備できた」という約束であり、「任意のアプリの必須機能をすべて満たす」という約束ではない。外部アプリのABI・必須機能・RAM・スタック・権限は、起動前に別途照合する。満たせなければAPP_LAUNCH_FAILEDとして扱い、成功を捏造しない。利用可能でないI/OをOS_READY後に初めて初期化し、その待ち時間を隠すことはしない。遅延接続等を採用する場合は、準備済みサービスと未完了操作をAPIで区別する。

## 4. 責任と依存関係

| 構成要素 | 責任 | 禁止する依存関係 |
|---|---|---|
| 起動・初期化 | CPU、メモリ、時計、必要なコントローラーとサービスを準備 | 診断の全ページ表示、キー入力、ページ送り完了を待つ |
| OSランタイムのサービス管理 | USB、ファイル、通信のセッション・DMA・継続処理・停止を所有 | 診断ビューの寿命をI/Oセッションの寿命にする |
| 起動状態・診断記録 | 成否、時刻、機器、エラーと観測結果をRAMに保持 | 記録更新時に必ず描画する |
| 診断ビュー／アプリ | 記録の整形、一覧、ページ送り、画面構成 | 開閉だけでコントローラーをリセット・解放する |
| 異常時の最小出力 | 起動失敗の位置と原因を可能な範囲で表示 | 通常ビューやヒープの正常性を必須にする |

OS側の表示基盤、GOP情報の取得・検査・安全なマッピングは残す。フォント、詳細表、複数ページ、装飾を初期化の必須処理から外す。

初期化から記録への一方向の通知と、ビューから記録を読む経路を基本とする。OSの初期化を、ビューが作成・描画されたことによって進めない。

## 5. 診断記録と描画

### 5.1 記録側

- 起動段階、サービス状態、機器ID、理由コード、時刻などを、容量上限のあるRAM領域へ記録する。
- イベント追加・状態更新は、それ自体ではフレームバッファへ書き込まない。
- 通常経路の大量な文字列整形は減らし、段階ID等を表示側で解釈できる形を優先する。既存形式からは段階的に移行してよい。
- 重複した更新では、描画だけでなく不要なdirty設定や記録追加も省けるようにする。
- 記録が満杯でも初期化を止めない。省略・上書き方針と欠落数を持ち、重大な直近エラーは別領域等で保持する。
- 早期に時計が使えない記録は連番を保持し、時刻は未取得とする。架空の時刻を入れない。

### 5.2 表示側

通常起動は非表示または最小限の概要表示を基本とし、全領域の繰り返しクリアをしない。初期化中の必須ではない説明画面は後回しにする。

詳細診断を選んだ場合だけ、明示的な描画関数を安全な処理点で呼ぶ。変更行・変更領域の描画、複数更新のまとめ処理、再描画頻度の制限を行う。更新頻度の制限に必要な時計がない段階は、重要な節目だけを表示する。

自動ページ送りと、そのための8秒待ち等は、通常起動から外す。診断表示として残す場合も、サービスの進行を妨げない構成とする。表示を遅延させても、それを待ってReady判定が進む設計にしない。

診断画面を非表示にする既存の`hide()`等があれば活用するが、表示抑制だけで記録・描画の責任分離が完了したとは扱わない。

アプリ実行開始後に、OSの常時オーバーレイを必須にしない。既存のファイルビューアーが描く画面へ、診断側が無断で上書きしない。アプリは必要に応じて起動状態のスナップショットを表示できる。将来の外部APIで返すのは、版付きの公開レコードであり、内部PanelやBootInfoへのポインターではない。

### 5.3 致命的エラー

表示基盤が利用可能な場合、通常表示が無効でも、最終段階・理由を最小限で示す。巨大な診断画面、ページ巡回、未初期化のヒープ、通常ビューのロック取得に依存させない。画面自体が使えない場合には表示成功を保証しない。

現在の単一CPU・割り込み禁止等の前提を守り、本変更だけのために共有データへ非同期アクセスを導入しない。将来の割り込み対応では、所有権・再入・スナップショット取得を別途設計する。

## 6. I/Oの所有権と寿命

**USB、ファイル読出し、ネットワークのサービスはOS側に属し、診断表示のための一時資源ではない。**

初期化処理から「準備済みのサービス状態」をOSランタイムへ引き渡し、その所有者が起動後の処理も継続する。初期化関数が戻った直後にDropや後処理で停止してしまうものを、利用可能として公開してはならない。

アプリは、OS側で管理したハンドルや検査済みのAPIを利用する。診断データ、アプリのファイルハンドル、コントローラー、DMA領域の所有者を区別する。

- 診断の開閉・表示モード変更では、USBリセット、NIC停止、再列挙、ファイルサービス解放を行わない。
- アプリ終了時には、そのアプリが所有するファイル等を閉じる。コントローラー全体を止めるかはOS側の終了方針で判断する。
- ファイル転送のキャンセルは、アプリの転送の終了であり、診断画面の切り替えでもOS全体の停止でもない。
- 正常停止・異常停止でのDMA停止確認、保留中転送の完了／中止、バッファ回収の順序を維持する。
- 安全な停止を確認できない資源は再利用しない。回復を捏造しない。

従来の`xhci::diagnose(...)`のように、初期化・実行ループ・後始末が一体になった関数が残っている場合は、内部の実際の寿命を調査する。単に関数名やモジュール名を変えるだけでは不十分。保持中のストレージ、複数コントローラー、キーボード、USBハブの現在の進捗を残して、段階的に分ける。

## 7. 初期化に残すもの・分離するもの

| 初期化に残すもの | 通常起動から分離するもの |
|---|---|
| メモリ範囲・重複・権限の検査、必要な初期化・ゼロ化 | アプリ用RAMの追加動作試験・大量なテスト走査 |
| 機器の識別、所有権取得、資源整合性検査 | 情報表示だけの追加走査・整形 |
| リセット完了・転送完了・仕様上必要な待ちと期限 | 撮影や説明のための固定秒数待ち |
| 実用I/Oを提供するためのリング、状態、サービス準備 | リング周回等を確認するための反復的な自己試験 |
| 必要なファイルシステムの検査とマウント | 指定テストファイルの全内容照合・結果ページ表示 |

「診断」という名前の関数にも実際の初期化が含まれ得るので、一括削除しない。診断を減らして初期化が不安定になる場合は、隠れていた待ち・順序・同期の不足を調べる。画面描画の遅さやsleepを仕様上の待ちの代わりにしない。

## 8. 起動時間の記録

記録する節目は、可能な範囲で以下とする。

| 記録 | 意味 |
|---|---|
| `efi_entry` | Musha-OSのEFI入口 |
| `core_ready` | CPU・メモリ等の基盤成立 |
| `os_ready` | 起動必須サービス利用可能・アプリへ移行可能 |
| `app_entry` | アプリの最初の処理へ移行する直前 |
| `first_frame_complete` | 表示APIが最初の画面反映処理をソフトウェア上で完了した時刻 |

OS初期化は`efi_entry → os_ready`、アプリ移行準備は`os_ready → app_entry`、アプリ初期化・初回描画は`app_entry → first_frame_complete`として分けて示す。

- Readyと時刻を確定してから表示する。描画完了時刻で起動完了時刻を上書きしない。
- 初期化中に実施した描画時間は、実際の起動時間から恣意的に差し引かない。描画そのものを削減する。
- 電源投入からEFI入口までの時間は別区間。未計測ならOS時間へ混ぜない。
- 早期の時間源がない場合は、計測開始点・未計測区間を表示する。異なる時計の数値を校正せず差し引かない。
- 時計の単位、分解能、起点、ラップ処理を記録する。PMタイマー等のラップを長い描画や試験がまたぐ点にも注意する。
- 初回描画完了は、ディスプレイが物理的に表示した時刻や垂直同期を保証する値ではない。OSの進捗表示や診断オーバーレイをアプリの初回画面として数えない。アプリからの任意の「利用準備完了」通知はapp_ready_reported等の別イベントにし、画面を使わないアプリのfirst_frame_completeは未取得のままでよい。
- QEMU結果と実機結果を分け、表示OFF／概要／詳細の条件と、同一構成での複数回の測定値を残す。
- 「必ず1秒」「瞬時」等の時間を、測定前に保証しない。

## 9. API・ABI・SDKの分離

### 9.1 3つの成果物

| 区分 | 定義するもの | 含めないもの |
|---|---|---|
| **API** | アプリが利用できる操作、その意味、エラー、上限、所有権、待機・終了の動作 | 特定言語の内部型、機器ドライバーの実装詳細 |
| **ABI** | 起動情報、外部アプリ形式、CPU条件、通常の言語間呼出し規約、システムコールの機械的契約 | Rust内部ABI、カーネル関数の生ポインター、OSの構造体そのもの |
| **SDK** | Cヘッダー／libmusha、Rust用musha-sys／musha、crt0、sysroot、リンク設定、サンプル、検査・デバッグ支援 | OS依存処理をアプリへ押し付ける仕組み、必須のGUIやイベントループ |

仕様の最終形は、次の構造とする。モジュール名は案で、既存の同等部分へ統合できる。

```text
Ring 3
  Cアプリ：main()                     Rustアプリ：任意のentry／ループ
       │                                     │
  libmusha / 任意のlibc               musha / musha-sys
       └────────── 小さな公開ABI ─────────────┘
                     システムコール
===================== 権限の境界 =====================
Ring 0
  引数・権限・バッファ・ハンドルの検査
                         │
  OSサービス：表示・入力・時刻・ファイル・通信・USB
                         │
  ドライバー／DMA／割り込み等の実装
```

実行時の経路は`アプリ → SDK → ABI → サービス`となる。APIは操作の意味を定め、SDKは使いやすい形を提供し、ABIは実装・言語の境界を安定させる。

### 9.2 現行APIは捨てず、公開境界と区別する

旧2.0作成時の参照点は公開mainの`322ee67`で、静的リンク向けの内部API版5とFAT32/exFAT逐次サービスが記録されている。本3.0の更新は既存文書と合意したABIの話を統合するもので、現在のローカル実装を再監査した記録ではない。`init / step / files / shutdown`等は必要な間は内部アダプターとして維持し、作業開始時のコードを再確認する。[R1]

外部アプリへ同じコールバックを強制しない。内部APIの変更番号を、新しい外部ABIの番号として流用しない。内部サービスから、型付きの結果を公開契約へ変換する検査層を置く。内部の`Again`再試行方式を、そのまま利用者の唯一の書き方にしない。

## 10. 起動状態と公開契約の接続

外部SDKに対して、以下の照会を設計する。名前は説明用であり、既存シンボルではない。

| 公開情報 | 例 | 注意 |
|---|---|---|
| 実行環境情報 | OS版、ビルドID、外部ABI版、実行プロファイル | 内部API版、SDK版とは別 |
| 起動レポート | CORE_READY／OS_READYの到達、時刻の取得可否・起点・単位 | 画面の文言を解析して取得しない |
| 機能照会 | 対応操作・上限と、現在のサービス状態 | 「コードに実装がある」と「この機器で利用可」を分ける |
| アプリへの許可 | ファイル読出し、特定USB機器等の権限 | 機能ビットが立つことだけで権限を与えない |
| アプリ起動情報 | 専有RAM／スタック、設定データ等 | ユーザー領域のコピーまたは安全な読み取り専用マッピング |

起動レポート・診断記録の取得は読み取り専用で、取得しただけでは描画や再初期化を行わない。ポインター、物理アドレス、内部オブジェクト、不要な機密情報を含む記録は公開しない。件数・文字列長・コピー量に上限を設ける。

OS_READYは、OS側サービスが維持され、その実行プロファイルで提供するAPIが利用できる境界である。公開Ring 3プロファイルでは、システムコール入口、復帰、ユーザーコピー、サービス処理の実行機会も成立していなければならない。内部APIだけが動く段階で「外部SDK対応のOS_READY」とはしない。

外部アプリの処理順序は原則として次のようにする。

```text
OS基盤 → 起動必須サービス → OS_READY
  → アプリELF・メタデータを検査
  → ABI／必要機能／権限／メモリを照合
  → ユーザー領域・起動情報を準備
  → APP_ENTERING（移行直前の記録）
  → Ring 3のcrt0 → C main()／Rust entry
  → APP_RUNNINGの実到達確認・任意の初回描画
```

計測の`app_entry`は移行直前のOS側時刻と明記する。実際のユーザー実行を確認した証拠（テスト時のCPL検査・最初の有効なシステムコール等）とは分ける。アプリ移行に失敗した場合を、APP_RUNNING成功として記録しない。

## 11. 公開APIの設計方針

### 11.1 小さなAPI群

| 機能群 | 最初に仕様化する操作 | 導入の範囲 |
|---|---|---|
| システム | ABI／機能／起動情報照会、ログ、終了 | 外部Helloの最小経路 |
| メモリ | 専有RAM情報、必要になれば領域追加 | malloc／GCはアプリまたはSDK側 |
| 時間・待機 | 単調時計、期限付き待機、複数イベントの待機 | I/Oを進めるためのpoll義務は課さない |
| 表示 | 画面情報、RAM上のサーフェスからの一括反映 | フォント・GUI・ウィンドウは任意のSDK側 |
| 入力 | 押下／解放、切断、入力欠落等のイベント | キー用途・レイアウト変換は層を分ける |
| ファイル | 一覧／識別、open、read／read_at、close | 現行の読出し専用範囲から開始 |
| 通信 | 対応方式の送受信、状態、期限・取消し | 未実装のUDP/TCP等を宣言だけで対応済みにしない |
| USB機器 | 必要な場合に、権限を限定した機器・転送操作 | 汎用の生USB APIは初版必須にしない |

最初からすべての関数を実装・公開しない。内部サービスを一つずつ接続し、機能照会とドキュメントで実装範囲を示す。未接続機能を黙って成功にするstubは禁止する。

### 11.2 共通のルール

- ファイル、接続、機器、要求、待機対象は、不透明ハンドルで表す。型・所有アプリ・権限・世代をOSで検査し、解放済みや別サービスのハンドルを拒否する。
- 成功／エラーと、転送したバイト数を分ける。EOF、部分完了、Again、Timeout、Canceled、Disconnected、Unsupported、NoMemory、Limit等の意味を統一する。名前と数値はABI仕様で固定する。
- 入力ポインターと長さの範囲全体を検査する。整数あふれ、未マッピング領域、読み書き権限、出力先の重なり等も定義する。複合要求は検査用コピーを取得し、検査後の変更で条件がすり替わらないようにする。
- 失敗時の出力バッファ、ファイル位置、ハンドルの状態を操作ごとに定義する。「常に出力不変」と「部分完了を返す」方式を混在させる場合は明示する。
- ファイル名はUnicode表現と原名の扱いを定義し、短縮した表示名で開き直さない。UTF-16名・FAT短名等を変換する際の未対応文字の扱いを決め、既存のID選択による取り違え防止を保持する。
- プロセス資源、キュー、要求数、転送量に上限を持つ。読まれないイベントや受信データを無限にためず、欠落・背圧を伝える。
- アプリへコントローラーレジスター、DMAリング、カーネル内部の生アドレスを直接与えない。

### 11.3 表示APIと初回画面

通常描画は、アプリ専有RAM上のバッファをOSへ渡して、矩形またはフレーム単位で反映する方式を出発点とする。1ピクセルごとにシステムコールを発行するAPIを標準描画経路にしない。

初期の同期presentは、幅・高さ・stride・pixel format・転送量・ポインターを検査し、戻るまでにOSによる読取りを終える契約にする。非同期presentを追加する場合は、OS側コピーまたは登録済みバッファの明示した所有権を使う。初回描画の完了は第8節の記録へ接続する。

文字描画・フォント・GUIは任意のSDK／アプリ側へ置く。ログ用の簡単な文字出力があっても、GUIや標準出力端末全体の提供と同一視しない。OSの致命的障害表示は別の最小経路として残す。

## 12. ABIの詳細化：標準部分とMusha-OS固有部分

### 12.1 採用方針と、この詳細案の確定度

**iBCS／iBCS2は採用しない。System V AMD64を基礎とする通常のC ABI、静的ELF64、Musha-OS固有の起動・システムコールABIを組み合わせる。** iBCS2は歴史的なi386 UNIXバイナリー互換環境に関係するものであり、本プロジェクトが目指す新しいx64アプリ向けの契約とは目的が異なる。[S11]

ELFやSysVの関数呼出し規約を使うことを、Linux／SCO等のバイナリー互換、POSIX準拠、System V実行環境全体の互換と説明しない。既存コンパイラーでMusha-OS向けにビルドすることが目的である。

本節は前回のABIの説明を、実装担当者が具体化できる**詳細設計案**へ落としたもの。以下の3区分を使う。

| 区分 | 扱い |
|---|---|
| **採用方針** | iBCS非採用、3種類のABIの分離、Ring 3、API・ABI・SDKの責任分担。実装完了を意味しない |
| **推奨プロファイル案** | ET_EXEC、no-red-zone、64byte起動情報、SYSCALL＋IRETQ、以下のレジスター割当など。Bで仕様・整合試験を用意し、Cの実装前にexperimental契約として固定する候補 |
| **未確定** | syscall番号、エラー数値、NOTEの符号化、実アドレス、上限、ツール版等。第12.10節の台帳で決め、仮の値を公開ABIにしない |

**文書版3.0、構造体名のv1、外部ABI major/minor、OS版、SDK版は別の番号である。** この文書の更新だけで、外部ABI 1.0等が公開・確定したことにはならない。既存のローカル実装が先行していれば、互換性と試験を調べて差を記録し、盲目的にこの案へ戻さない。

### 12.2 3種類のABIと、UEFI境界

| 契約 | 採用・設計する範囲 | 混同してはいけないもの |
|---|---|---|
| **通常のC ABI** | アプリ内のC関数、C／Rust FFI、型配置。SysV AMD64のLP64を基礎にする | Ring 0へ入る手段ではない |
| **アプリ形式・起動ABI** | ELF、メタデータ、CPU条件、Ring 3の最初のRIP／RSP、起動情報、crt0、終了 | Linuxの初期スタックや動的リンカーを暗黙に持ち込まない |
| **システムコールABI** | 特権境界の入口、番号、引数、結果、破壊・保存状態、引数検査、安全な復帰 | 通常のC引数配置やLinuxの番号・意味とは別 |
| **既存UEFI／カーネル境界** | 現行のefiapi／Win64等を必要に応じて維持 | 公開アプリのSysV化のためにカーネル全体のターゲットを一括変更しない |

SysVのSDKからUEFI向けにビルドしたカーネル関数を直接呼ばない。システムコール入口のアセンブリは、実際に呼ぶカーネル関数のABIへ明示的に接続する。Win64関数を呼ぶ場合は、その引数配置・スタック整列・shadow space等の条件も別に満たす。`extern "C"`の意味を、異なるターゲット間で同一と決めつけない。[S4][S5]

### 12.3 通常のC ABI：SysV AMD64／LP64

通常の関数呼出しはコンパイラーのSysV AMD64実装を利用する。次は基本部分の参照用要約であり、構造体分類や可変長引数を単純な独自規則に置き換える指示ではない。[S9]

| 項目 | 基本条件 |
|---|---|
| データモデル | LP64。int 32bit、long／ポインター64bit。公開レコードは固定幅整数を使う |
| 基本整数・ポインター引数 | RDI、RSI、RDX、RCX、R8、R9。その後は規則に従いスタック |
| 基本浮動小数点引数 | XMM0～XMM7。複合型等はpsABIの分類に従う |
| 戻り値 | 型に応じRAX、RDX、XMM等。大きい構造体等もpsABIの分類に従う |
| callee-saved GPR | RBX、RBP、R12～R15。RSPを復元する |
| 基本の整列 | 通常call直前はRSP % 16 = 0、通常の関数入口はRSP % 16 = 8。型による追加整列は別途従う |
| Direction Flag | 通常の関数境界でDF=0 |

**初期SDKの推奨はred zoneを使用しないビルドプロファイル。** Cは`-mno-red-zone`、Rustと全ての依存オブジェクトも同条件にそろえる。SysVが定義する128byteのred zoneを利用する既成オブジェクトは、必要な保存保証を検証するまで一般対応としない。[S9]

no-red-zoneは、OSがユーザースタックを勝手に作業領域へ使ってよいという意味ではない。ユーザーからの例外・割り込み・syscallではカーネル用スタックを使い、ユーザーの有効なメモリを破壊しない。red zoneの使用有無をELF一般情報だけで完全に判定できるとは限らないため、SDKの生成条件・メタデータ・試験で管理する。

C APIは固定幅の状態値とハンドルを中心にし、可変長引数や浮動小数点をOS呼出しの必須引数にしない。ただし**アプリの通常計算やC／Rust間のdouble等まで禁止するわけではない**。Cのlong double、拡張整数・複合型などは対応範囲を明記し、未検証の型まで全面互換と呼ばない。

### 12.4 外部アプリの実行形式・ローダー契約

OS起動用は既存の`BOOTX64.EFI`、外部アプリの初期候補は次の形式とする。ELFのPT_LOAD、BSS、配置整列の意味は標準を参照し、その上にMusha-OSの限定を置く。[S10]

| 項目 | 推奨プロファイル案 |
|---|---|
| 識別 | ELFCLASS64／ELFDATA2LSB／EM_X86_64 |
| 形式 | 静的ET_EXEC。位置はユーザー仮想アドレスで定義 |
| ロード単位 | Program HeaderのPT_LOAD。セクション名やセクション表を実行時の必須条件にしない |
| コード・データ | コードは読出し・実行、データは読書き・実行不可。ページ単位でW^Xを守る |
| スタック・Arena | 別領域。読書き・実行不可。スタックにガード領域 |
| 未提供 | PIE／ET_DYN、動的リンカー、動的依存、実行時再配置、TLS、32bit互換実行 |
| 初期ASLR | 必須にしない。非採用の制限を記録し、将来の別プロファイルで検討 |

固定するのは必要なユーザー仮想配置であり、物理RAMではない。ロードアドレス、ユーザー領域の上下限、スタック／Arenaの配置、ページサイズ、最大セグメント数・イメージ容量は第12.10節で確定する。CPUの「canonicalなアドレス」という条件だけで許可せず、OSが割り当てたユーザー領域内か検査する。

ローダーとSDK側のapp-checkに、同じ検査規則と良品・不正イメージのfixtureを用意する。

- ヘッダーサイズ、バージョン、件数、ファイル範囲、整数あふれ、対応machine/classを検査する。
- PT_LOADについてfilesz <= memsz、ファイル範囲、仮想範囲、align、offsetとの整合を検査する。memszにだけ存在する末尾はゼロ化する。
- セグメント重複とページ境界の共有を扱い、最終的なページ権限がW+Xにならないことを検査する。初期版で共有を拒否するなら、リンカースクリプトと合わせて明記する。
- 入口は有効な実行セグメント内とする。OS領域、スタック、Arena、起動情報と重ならないことを確認する。
- PT_INTERP、PT_DYNAMIC、PT_TLS等の非対応要素を検出して拒否する。非LOADヘッダーは種別ごとの受入・無視・拒否を定義する。未知の実行上必須機能を黙って無視しない。
- デバッグ情報や静的リンク時に処理済みの再配置情報がファイルに残っていることと、実行時再配置が必要であることを区別する。デバッグセクションの存在だけで不正扱いしない。
- 不正・対応外ならRing 3へ入る前にAPP_LAUNCH_FAILEDとし、OS_READYの過去記録は改変しない。

**NOTE案：** ELF内にMusha-OS専用NOTEを持たせ、識別名・形式版、要求ABI major/minor、CPUプロファイル、必要サービス、要求権限、Arena／スタック量を記録する。NOTEの名前・type・fields・整数幅・整列・重複時の扱いは未確定。採用するx64 psABIと実際のClang／LLD出力を照合して固定し、C構造体の生コピーを無検査でNOTEとみなさない。外部設定と食い違う場合は拒否または明示した優先規則に従う。

NOTEは対応条件の宣言であり、署名や安全性の証明ではない。ELF OSABI欄だけでも判定しない。要求された権限はOS側の許可と照合する。ホストのapp-checkはカーネル検査を省く理由にはならず、全機械語の安全性を保証するものでもない。

### 12.5 Ring 3の起動ABIと、64byteの起動情報案

最初の遷移先はアセンブリの`_start`とし、通常のC関数へ直接jumpしない。SDKのcrt0が起動情報を確認し、必要な初期化の後で`int main(void)`またはRust entryへ通常callする。mainの戻り値は終了syscallへ渡す。初期版はLinuxのargc／argv／envp／auxvやPOSIXの終了状態符号化を要求しない。

| 起動状態 | 推奨案 |
|---|---|
| RIP | 検証したELF entry |
| RSP | ユーザースタックの上端、16byte整列。直下は有効な書込み可能スタック |
| RDI | 公開起動情報へのユーザー仮想アドレス |
| RBP | 0 |
| その他のGPR | 指定入力以外は0を初期値案とし、カーネルの値を漏らさない |
| CPL | 3。CS／SSはOSが用意したユーザーセレクター |
| フラグ | DF=0、IOPL=0。割り込み入口等の準備後、IF=1で開始する案。その他は許可する値を明示して初期化 |
| FS／GS | 初期版はアプリTLSを提供しない。ユーザー側base等を初期化し、カーネル用状態と区別 |
| FPU／SIMD | 対応CPUプロファイルの既知の初期状態にする。以前の実行状態を漏らさない |

**`_start`入口のRSP % 16 = 0と、通常のC関数入口のRSP % 16 = 8は矛盾しない。** 前者はcallされていない入口で戻りアドレスがなく、crt0からのcallで通常の整列になる。crt0が何かpushする場合は、次のcall前に再調整する。`_start`からretしてOSへ戻る契約にしない。

以下は**未公開のレイアウト案**。型名のv1はレコード案の名前であり、外部ABIを正式版1.0に設定する指示ではない。`struct_size=64`を初期案とする。

```c
#include <stdint.h>
#include <stddef.h>

typedef struct musha_start_info_v1 {
    uint32_t struct_size;        /* offset  0 */
    uint16_t abi_major;          /* offset  4 */
    uint16_t abi_minor;          /* offset  6 */
    uint32_t flags;              /* offset  8 */
    uint32_t reserved0;          /* offset 12: zero */
    uint64_t arena_base;         /* offset 16: user virtual address */
    uint64_t arena_bytes;        /* offset 24 */
    uint64_t stack_base;         /* offset 32: mapped usable range */
    uint64_t stack_bytes;        /* offset 40: guard pages excluded */
    uint64_t boot_report_handle; /* offset 48: zero if unavailable */
    uint64_t reserved1;          /* offset 56: zero */
} musha_start_info_v1;

_Static_assert(sizeof(musha_start_info_v1) == 64, "start info size");
_Static_assert(_Alignof(musha_start_info_v1) == 8, "start info alignment");
_Static_assert(offsetof(musha_start_info_v1, arena_base) == 16, "arena offset");
_Static_assert(offsetof(musha_start_info_v1, boot_report_handle) == 48,
               "boot report offset");
```

Rust側も同じ定義元または整合検査で生成・維持する。以下もレイアウト説明用であり、使えるSDKの提供ではない。

```rust
#[repr(C)]
pub struct MushaStartInfoV1 {
    pub struct_size: u32,
    pub abi_major: u16,
    pub abi_minor: u16,
    pub flags: u32,
    pub reserved0: u32,
    pub arena_base: u64,
    pub arena_bytes: u64,
    pub stack_base: u64,
    pub stack_bytes: u64,
    pub boot_report_handle: u64,
    pub reserved1: u64,
}

const _: () = {
    assert!(core::mem::size_of::<MushaStartInfoV1>() == 64);
    assert!(core::mem::align_of::<MushaStartInfoV1>() == 8);
    assert!(core::mem::offset_of!(MushaStartInfoV1, arena_base) == 16);
    assert!(core::mem::offset_of!(MushaStartInfoV1, boot_report_handle) == 48);
};
```

起動情報は8byte以上の整列で、必要な範囲全体が読み取り可能なユーザー領域にあることをOSが保証する。専用の読出し専用・実行不可ページ等でアプリ存続中保持し、Arenaやスタックから分離する。64byteを含むページにカーネルの別情報を同居させない。新たにユーザーへ見せるページは初期化する。

arena_baseはアプリが使うユーザー仮想領域の先頭であり、物理アドレスではない。Arenaはアプリのmalloc／GC等に任せる。stack_bytesにガードページを含めない。boot_report_handleが0なら照会不能とし、架空の成功を返さない。追加の引数・設定・初期ハンドル群が必要なら、レコード拡張等を別途設計し、reserved欄へ勝手な意味を与えない。

### 12.6 システムコールABIの候補

**x64の入口はSYSCALL、初期のユーザー復帰は安全性を確認したIRETQを第一候補とする。** SYSRETによる最適化は後続とし、性能だけで先行しない。実装前にCPU要件、カーネルスタック、復帰、割り込みの設計を固定する。

前回説明の候補を以下にまとめる。Linuxのx64と同じ引数レジスター順を使うが、**呼出し番号、意味、結果規約、errnoはLinux互換ではない。** 特にRAX=状態、RDX=結果はMusha-OSの独自案である。SYSCALLがRCX／R11を使い、RSPを切り替えない点はLinuxの入口実装にも明示されている。[S12]

| 用途 | 候補の割り当て |
|---|---|
| 呼出し番号 | RAX。符号なし番号として扱い、範囲外を切り詰めない |
| 引数1～6 | RDI、RSI、RDX、R10、R8、R9 |
| 成功状態 | RAX=0 |
| エラー状態 | RAX=負の状態値。公開int32_t範囲を64bitに符号拡張する案 |
| 主結果 | 成功時RDXにbyte数・ハンドル等。主結果なし、またはエラー時は0とする案 |
| 大きい結果 | 検査済みのユーザーバッファへ返す |
| 変更され得るGPR | RAX、RDX、RCX、R11 |
| 保存するGPR | RBX、RBP、RSP、RDI、RSI、R8、R9、R10、R12～R15 |
| フラグ | 条件フラグの保持を約束しない。復帰時DF=0、IOPL=0等の安全条件はOSが維持 |
| FPU／SIMD | 対応プロファイルで公開したユーザー状態は、raw syscallの前後で保持する |

**RDXは第3引数と結果の両方に使う。** ラッパーは入力と出力を同じレジスター制約として扱い、戻った値を元の第3引数と誤認しない。第4引数のRCX→R10変換はSDK側の責任。Cの6引数wrapperでは、通常C ABIとraw syscall ABIを別に検証する。

raw syscallの保存保証と、CのSDK関数を呼んだ際の保存保証は別である。SDK関数は通常のSysV C ABIに従うので、コンパイラーがcaller-savedレジスターを使用することはある。アプリがSDKのC関数呼出し全体について、raw syscallの保存保証を仮定してはいけない。

C APIは`int32_t`状態値と出力引数を使い、SDKがRAX／RDXから変換する方式を候補とする。Rustでは低レベル値を`musha-sys`に閉じ込め、安全な層でResult等へ変換する。RustのResultをraw ABIへ載せない。asm wrapperを使うなら、RCX／R11／RDX／flagsとメモリ副作用をコンパイラーへ正確に伝え、I/Oをpure／nomem／preserves_flags等として誤って宣言しない。

番号とエラー数値は未採番。Bで照会・ログ・終了から表を作り、整数幅・拡張規則と一緒に決める。未知の番号と、既知だが利用不能なサービスは別に表現する。Linuxの番号やerrnoを流用したと暗黙に解釈しない。エラー時のRDX=0は「副作用が必ずない」という意味ではなく、操作ごとに部分完了・位置・出力の契約を定める。

### 12.7 カーネル入口・復帰・非同期割り込み

SYSCALLでユーザーRSPを保存してカーネルRSPへ切り替えるまでの区間を、コンパイラー任せの通常関数にしない。TSSのRSP0だけでSYSCALLのスタック切替が済むと思わない。TSS／ISTは、ユーザーからの割り込み・例外等の経路と合わせて設計する。[S12]

C工程へ進む前に、以下を設計・検査する。

1. SYSCALL用MSR、ユーザー／カーネルセレクター、入口がアクセスできるページ、カーネルスタック、ユーザーRSPの保存場所を定義する。
2. 入口のRFLAGSマスク、DF等のクリア、割り込みを受けられる安全な時点を決める。NMI・例外・再入が起きてもユーザースタックをカーネル作業用に使わない構成とする。
3. カーネルが触る前に、必要なユーザーGPR／FPU／SIMD状態を保存する。通常C ABIでcaller-savedでも、非同期割り込みで勝手に壊してよいことにはならない。
4. カーネル関数の実ABIに合わせて呼び出す。既存efiapi／Win64と公開SysVの違いを、引数・整列・shadow spaceを含めて橋渡しする。
5. 復帰先RIP／RSP、CS／SS、RFLAGS、ユーザーアドレス空間を検証する。非canonical値、禁止領域、権限昇格するフラグを拒否する。スタック上端のような境界値も契約どおり扱う。
6. IRETQでの検証済み復帰を実装・試験する。SYSRETへ進む場合も同じ公開契約を保ち、異常な復帰先やCPU差を別途試験する。
7. ユーザーポインターの範囲検査に加えて、コピー中の障害をカーネル破損にしない。必要なページの寿命と、検査後に内容が変わる場合のコピー・所有権を設計する。
8. 起動前、syscall中、アプリ実行中、I/O待機中、終了処理中の例外を区別する。ユーザー失敗をOSの内部成功ログで隠さない。

具体的なMSRビット、例外フレーム、保存方式はIntel／AMDの対応マニュアルで確認し、対象CPUの範囲を記録する。Linuxの実装は手順の参照であり、そのコードやLinux固有の最適化をそのまま取り込む指示ではない。取り込みが必要なら元ライセンスとプロジェクト方針を確認する。[S12][S16]

### 12.8 公開データ・ハンドル・互換性

固定幅整数、明示的な長さ、公開レコード、ハンドルを使う。OS境界にCのlong／bitfield／実装依存enum幅やRustの通常のenum／Result／Vec／String／参照／trait objectを使用しない。repr(C)はレイアウト指定であり、ポインターの有効性・所有権を保証しない。[S5]

**レコードの規則案：** inputの最小長・上限を決め、未知の必須フラグとゼロでない予約欄を拒否する。既知サイズを超えるinputを許す場合は、上限と未知末尾のゼロ確認等を具体的に定義する。outputは呼出し側capacityを別引数として検査し、実際に返した長さと必要長を区別する。OSが返すpaddingと予約欄は初期化する。任意のstruct_sizeを無制限コピーに使わない。[S6]

**ハンドルの規則案：** uint64_t／u64、0は無効値。公開される数値はカーネルポインターではなく、型・所有アプリ・権限・世代と対応する。値のビット配置はアプリに解釈させない。クローズ後・取消し後・アプリ終了後の値の扱いを定義し、世代枯渇で黙って再利用しない。

**版の規則案：** 文書版、OS版、内部API版、外部ABI major/minor、SDK版、CPUプロファイルを区別する。ABIの互換範囲と最低minorの照合を定義し、不一致は実行前に拒否する。OSが新しいminorであるだけで、要求機能が利用可能と判断しない。互換性を保証した呼出し番号を別用途へ再利用せず、既存フィールドの位置・意味を互換性の範囲内で維持する。古いSDKで生成したELFを保存して再実行試験する。

ABIの最初の識別はELFメタデータと起動情報で行う。未対応ABIのアプリを走らせてから、意味が合わない照会syscallで互換性を交渉する設計にしない。

I/Oの所有権、同期・非同期、キャンセル、DMAの寿命は第11・14節に従う。64bitポインターを受け取れるから、任意のユーザーポインターを後続DMA先として保持してよいわけではない。readの部分成功、EOF、Again、出力不変性等はAPI契約で定め、レジスター表だけで決めない。

### 12.9 CPU・浮動小数点・Clang／Rustターゲット

**推奨プロファイルは、NUC5相当のx64機を念頭に置く基本x86-64＋SSE2、LP64、no-red-zone。** 互換性の入口表記は「x64機、NUC5以上を想定」とし、実際の可否はCPU機能・ファームウェア・機器・OS実装で判定する。NUC5という名前だけでSSE／FPU保存や全周辺機器の対応を証明しない。

AVX／AVX2／AVX-512等の拡張状態を初期SDKの既定にしない。必要なCPU機能は機能集合として固定し、CPUID上の存在とOSによる有効化・保存対応を区別する。ユーザーに使用を許す拡張状態が増える場合は保存範囲も増やす。`-march=native`を配布アプリへ使用しない。

SSE2対応を宣言する前に、x87／MMX／XMM／MXCSR等のどの状態を使えるか、初期値、保存・復元、例外処理を定義する。FXSAVE／FXRSTOR等を使う初期方式、またはXSAVE系を選ぶ場合の対象state・領域・整列を決める。カーネル内のmemcpyや最適化がSIMDを使う可能性も評価し、対応状態を保存する前に破壊しないようにする。整数だけのHello成功では、浮動小数点対応の合格にしない。

Rustの既成`x86_64-unknown-none`は、そのままClangの通常SysV浮動小数点ABIと一致すると扱わない。公式文書はベクトル・浮動小数点レジスター不使用とkernelコードモデルを説明しており、参照したターゲット実装にも`RustcAbi::Softfloat`が指定されている。[S4][S13]

そのため、**通常SysVのfloat／double等を共通に扱う最終SDKでは、ABIが一致するRustターゲットとライブラリを選ぶ。** 必要ならMusha-OSのユーザー向けcustom targetを用意し、core／必要なalloc・補助ライブラリまで同じ設定でビルドする。単にtarget-featureへSSE2を追加したりsoft-floatを消すだけで、既成ライブラリやFFIまで整合したと判断しない。

custom target JSONの項目は安定仕様ではない。`build-std`を使う方法にもnightly、rust-src等の条件がある。SDKで採用するrustc／Cargo／ターゲット定義／標準ライブラリソースを固定し、実際のJSON schemaと生成結果を検査する。ユーザーSDKのためにカーネルの既存toolchainまで無条件にnightlyへ移さない。[S14][S15]

Clangの対象triple、sysroot、LLD、コードモデル、静的リンク、再配置の扱い、red zone、FP／SIMD、stack protector／TLS、panic／unwindを一つのビルドプロファイルで記録する。小さいコードモデルは選んだ仮想配置に合う場合に採用し、巨大Arenaへのアクセス等とは区別して検査する。

初期版はTLS、言語例外のカーネル越境、C++の全面的なランタイム対応を要求しない。Cのlong doubleは通常のx64ターゲットでx87を使う場合があるので、C内での対応試験とRust FFIでの対応型を分ける。float／doubleのC↔Rust、構造体混在、スタック渡し、割り込み・syscall前後の状態保持を通してから共通プロファイルの対応を宣言する。

### 12.10 詳細値の台帳と固定手順

Bで、既存の相当文書がなければ`docs/application-abi.md`に次の台帳を作る。実装上の定数は一つの定義元を持ち、仕様・C・Rust・カーネル表・検査ツールを整合させる。案を変更する場合は理由と互換性への影響を残す。

| 項目 | 本書の状態 | 固定・検証する時点 |
|---|---|---|
| iBCS非採用／3境界分離 | 採用方針 | 直ちに文書へ反映 |
| 通常C ABI | SysV AMD64／LP64を基礎 | Bで対応型・red zoneを記録し、CでFFI実行試験 |
| ELFプロファイル | 静的ELF64 ET_EXEC案 | Cのローダー実装前 |
| 起動情報 | 64byte・8byte整列のレイアウト案 | Bで全offsetを検査、Cの初回ロード前に実装と一致させる |
| 初期RIP／RSP／RDI／フラグ | 第12.5節の候補 | CのRing 3遷移実装前 |
| syscall入口・結果 | SYSCALL／IRETQ、RAX=状態・RDX=結果案 | Bで仕様・wrapper雛形、Cで往復試験 |
| 番号・エラー値・フラグ | **未採番** | Bで台帳作成。正式な互換性固定は実行試験後 |
| NOTEの符号化・CPU ID・ABI値 | **未確定** | Cのapp-check／ローダー前 |

Bの段階で候補を仕様・コンパイル可能な定義へ落とし、`experimental`なリビジョンとして記録することは認める。**公開ABIを固定したこと、ゲストで実行できたこと、実機で動いたことは別々に判定する。** 仮実装の成功stubやホストmockだけで公開契約を完成扱いにしない。


## 13. SDKの設計方針

### 13.1 標準ツールを利用する

Cは標準のClang、ELFリンクはLLDを利用し、Musha-OS専用コンパイラーのフォークを前提にしない。ホストはまず開発中のMacを基準とし、将来Linux等でも同じターゲット成果物を作れる構成にする。Clangのクロスコンパイル機能とLLDのクロスリンク機能を利用する。[S1][S2]

SDKには、最低限以下を用意する。以下は目標構成であり、未生成の実ファイルを使用可能と案内しない。

```text
sdk/
  sysroot/include/musha/      公開C API／ABI用ヘッダー
  sysroot/lib/               crt0.o、libmusha.a、必要な補助ライブラリ
  rust/musha-sys/             低レベルABIとシステムコールwrapper
  rust/musha/                 所有権とエラーを扱う安全なwrapper
  linker/                    ELF配置、エントリー、セグメント規約
  cmake/                     Clang＋LLDのtoolchain設定
  tools/                     ABI整合・ELF検査・QEMU runner・配布物生成
  examples/                  hello-c、hello-rust、I/O利用例
```

ホストのmacOS／Linuxのlibc・crt・SDKが意図せずリンクされないよう、ターゲット、sysroot、検索パス、実リンカーを固定する。`--target`や`--sysroot`だけを記載して完成とせず、生成物の形式・依存シンボル・リンクマップを確認する。[S1]

### 13.2 C側

Cの薄い`libmusha`がシステムコールを包み、crt0が公開起動情報を受け取って`main()`を呼び、戻り値を終了コードとしてOSへ返す。必要な標準ヘッダー、メモリ操作、compiler-rt等のターゲット補助コードを用意する。`-ffreestanding`だけではライブラリ実装は供給されない。[S3]

最初は最小のC環境を明記し、malloc、stdio、数学ライブラリ等は段階的に整える。libcを採用する場合は対応するsyscall接続、ライセンス、既存コードとのABI一致を検証する。POSIX全面準拠、C++例外／RTTI／std全体を、この段階の必須条件にしない。TLSやstack protectorなどが補助ランタイムを要求する場合も、黙ってホストの実装をリンクせず、提供・不提供とビルド条件を明記する。

### 13.3 Rust側

`musha-sys`にunsafeを要する生の受け渡しを閉じ込め、`musha`でハンドルの所有権・寿命・エラーを包む。通常終了のDropは補助であり、異常終了時の回収をDrop任せにしない。`no_std`＋`core`を基本とし、アロケーターを持つアプリは任意で`alloc`を利用する。`std`対応を暗黙に約束しない。[S4][S5]

アロケーター、GUI、フォント、async executorは選択式とする。CでもRustでもmain／entry以後の実行構造を自由にし、OS固有のstepや定期pollを最終SDKの必須契約にしない。

ユーザー向けRustターゲットは第12.9節に従ってClang側との浮動小数点ABIまで合わせる。custom target、core／alloc再ビルドが必要な場合はSDKの構成と手順へ含め、既成x86_64-unknown-noneとの混在をABI検査なしに許さない。

### 13.4 開発体験と配布

CMake toolchainと直接のClang／LLD呼出しの両方を文書化する。CMake利用時はcompile_commands.json等のIDE情報を用意し、実ターゲット条件と一致させる。Cargoには必要なターゲット・リンカー・runner設定を用意する。[S7][S8]

SDKの移動・空白を含むパス・別のサンプルディレクトリでもビルドできることを試す。ローカルの絶対パスやOSの私有ヘッダーに依存させない。デバッグ用のシンボルと配布用ELFを対応付け、ホストのテストとQEMUゲスト実行を区別する。

SDK配布は当面GitHub Releasesの追加成果物でよい。OS本体、アプリ更新用ファイル、SDKを区別し、SDK版／対応ABI／toolchain版／ソースcommit／チェックサムを記録する。本作業ではReleaseの公開や既存配布物の差し替えは行わない。

## 14. 同期・非同期I/Oとアプリの自由

OSサービスは要求・完了・取消し・待機の共通状態を持ち、SDKは必要に応じて同期関数、イベント方式、Rustの任意のasync wrapperを提供する。async runtimeや一定周期のpollをアプリへ強制しない。

最小の外部Helloでは、ログ・照会・終了だけを提供してよい。現行の協調ランタイムに同期APIの名前だけ追加し、OSサービスが止まる待ち方を隠してはならない。実用I/Oの公開には、次を満たす必要がある。

1. アプリがAPIを呼ばずに計算していても、OS側の必要なI/Oとタイマーが進む。
2. 同期待機はアプリの待機であり、OS全体の停止ではない。待機登録と完了確認の競合で通知を取り逃がさない。
3. 非同期要求はIDと世代を持ち、古い・重複した完了を拒否する。アプリの任意ポインターを後のDMA先として保持しない。
4. 初版はOS所有の上限付きバッファを中心にし、受領時にユーザーへコピーする。共有・登録バッファやゼロコピーは別の詳細契約なしに導入しない。
5. Future破棄やcloseでアプリ側の関心がなくなっても、投入済みDMAの停止／完了まではOSが状態を保持する。キャンセル受付と、資源再利用可能を区別する。
6. ユーザーの長い計算はそれだけで異常扱いしない。OSは有限な入力・受信キューと欠落／背圧を明示する。

割り込みハンドラーとシステムコールでサービス状態を無秩序に再入させない。lwIP等の直列実行条件、カーネルスタック・FPU状態、割り込みマスク区間、タイマー期限をOS内部で整える。Ring 3への移行だけで、I/Oの独立進行や完全な障害隔離が完成したとは扱わない。

## 15. 段階的な実装と今回の範囲

**直近の必須範囲はA＋B。C・Dは後続の実装段階とし、起動分離の完了や現行リリースを待たせる新しい必須条件にはしない。** 既にC・D相当へ着手している場合も、その進捗は保持し、成果を独立して報告する。

| 段階 | 作業 | ゲート／成果物 |
|---|---|---|
| **A：起動と表示の分離** | 現状計測、記録と描画の分離、OS側のI/O所有権、Ready状態、診断アプリ分離 | 現行実行モデルで必須APIがOS_READY後に使え、描画でサービス状態が変わらない |
| **B：API・ABI・SDKの土台** | 操作意味の仕様、起動・CPU・syscall ABI案、単一定義元とC／Rust整合検査、独立SDKの構成・ビルド雛形 | ヘッダー／型／ビルド設定の整合をホストで確認。未実装のゲスト実行は未検証と表示 |
| **C：外部アプリの最小経路** | ELFローダー、Ring 3、最小syscall、crt0、C／Rust Hello | 同じOSバイナリーで別々にビルドしたhello.elfを起動・終了。CPLと境界保護を確認 |
| **D：実用I/OとSDK** | 表示・入力・逐次ファイル・対応通信、待機・取消し、アプリと独立したI/O進行 | 通常ループと同期APIで利用でき、長い計算・切断・異常終了でもOS契約を維持 |

A内は、観測 → 記録／描画分離 → Ready契約 → I/O寿命移管 → アプリ開始位置 → 回帰試験の順とする。BはAと並行できるが、Aの完成を大型SDKの完成へ依存させない。

Bでは、未完成のローダーやsyscallを模擬して「外部アプリが動いた」と報告しない。ホストmockはデータ配置・wrapper等の試験用途と明示し、ゲストの実機能とは分ける。実際のSDK機能はimplemented／experimental／plannedで示す。

Cの実装に進む際は詳細設計を先に確定し、共有状態へ割り込みを導入する変更をAの小変更に紛れ込ませない。Cだけの短いHello成功は、任意のアプリを実用的に受け入れるDの完了とは別である。

## 16. 受け入れ条件

### 16.1 A：起動分離

1. 記録更新だけでは描画ゼロ。重複更新でも不要な描画をしない。
2. CORE_READY → OS_READY → アプリ入口の順序と、Readyの一回性を検査する。
3. 必須サービス失敗でReadyにせず、任意機能不在は理由を記録して有界に進める。
4. Ready直後に必須APIが使え、初期化関数が戻ってもサービスが失効しない。
5. 診断OFF／概要／詳細で機能・安全条件を保ち、開閉でUSB／NIC／ファイルを停止しない。
6. 自動ページ巡回の待ち、反復RAM診断、表示専用の大量再走査を通常起動から外す。安全に必要な検査は保持する。
7. ログ満杯、小画面、長い描画、時計未取得、初期化失敗でも状態と原因を保持する。
8. USB・入力・FAT32/exFAT・取消し・切断・期限切れ・通信の既存回帰を維持する。
9. 描画OFFで初期化が不安定なら、偶然の描画待ちに依存した同期を修正する。待ち時間の無制限化で隠さない。
10. 同じ実行時間やタイミング依存のセクター数を合否基準にせず、状態と実データの整合で検査する。

### 16.2 B：仕様とSDKの土台

- API・ABI・SDKの責任、既存内部APIとの移行、提供範囲が文書とファイル構成で区別されている。
- CとRustで型のサイズ・アラインメント・オフセット・定数が一致する。生成元から再生成して差分がない。64byte起動情報案は全フィールドで検査し、対象x64の結果とホスト固有結果を分ける。
- 第12.10節の台帳が存在し、推奨案・experimental採番・未確定・実装済み・公開互換性固定の状態を分けている。
- 通常C ABIのRCXとsyscallのR10、第3引数兼結果のRDX、_startと通常C関数のRSP整列を定義・コンパイル検査する。実際の特権往復がなければ未検証と記録する。
- 最小CヘッダーとRustのno_std側を、それぞれターゲット向けにコンパイルできる。SDK版と外部ABI版を混同しない。
- Clang／LLDの実際の起動コマンド、ターゲット、sysroot、必要ライブラリと未提供範囲が明確。ホストライブラリ混入を検査する。
- ローダー／syscallが未完成なら、その実行試験は未実施と記録する。雛形を公開済みSDKと表示しない。

### 16.3 C・D：後続の外部アプリ受け入れ

- C／Rustで独立ビルドしたELFを、同じOSバイナリーへファイル差し替えだけでロードできる。OSファイルのハッシュ不変も確認する。
- 起動ABI不一致、未対応CPU、必要機能不在、不正ELF、禁止領域・古いハンドルを拒否する。
- 実CPL=3、user／supervisorページ属性、スタック保護、異常syscallと安全な復帰を検査する。
- C→Rust／Rust→Cの両方向で整数、float／double、混合構造体、6整数引数を超えるスタック渡し、対応範囲の返却規則を検査する。必要なら8浮動小数点引数超やsretも含める。
- RDI起動情報、全offset、_start／mainのスタック整列、BSSゼロ化、予約ページ保護を実ゲストで検査する。
- raw syscallの第3引数とRDX結果を違う値で試し、第4引数R10、エラーの64bit符号拡張、保存GPR、不正番号・復帰先を検査する。
- 対応を宣言するx87／XMM／MXCSR等の状態をsyscallと非同期割り込みの両方で検査する。通常のC callee-saved規則だけでは代用しない。Rust Softfloat設定との不一致を見逃さない。
- 長い計算中のI/O進行、期限付きwait、取消し／通知競合、切断、アプリ異常終了とDMA回収を確認する。
- 初回描画完了をOS_READYと分ける。表示しないアプリも実行できる。
- 互換性を約束した旧ABIアプリが後続OSでも動くことを固定fixtureで試す。

全段階で通常版とdebug／故障注入／probe版を分ける。ホスト・QEMU・実機の結果を混同しない。実機がなければ実機試験だけを未実施として残し、独立した文書・コード・ホスト／QEMU作業は進める。

## 17. 文書・配布物・既存作業の扱い

本書を統合方針の入口とし、詳細は既存の相当文書へ統合する。必要なら`docs/application-api.md`、`docs/application-abi.md`、`docs/sdk.md`を作るが、同じ契約を矛盾する複数文書で維持しない。第12節の候補をapplication-abi.mdへ固定した後は、値の正本を明示して本書と指示書は参照に寄せる。内部契約の`docs/app-api.md`を勝手に公開ABIへ改名・置換しない。

README、開発手順、将来設計、実行責任分担、Ready検査のスモーク試験を整合させる。実装前のRing 3を実装済みとは書かない。既存の英語先行・日本語併記規約があれば、リポジトリへ反映する際に従う。

通常USB更新はファイルのみとする。全媒体イメージ生成・全容量ハッシュ・フォーマットを通常更新へ戻さない。SDKを使ったアプリ差し替えも、媒体構成の変更を必要としない設計にする。

この依頼ではローカルの文書・コード・試験・ビルド準備まで。commit、push、タグ／Releaseの作成・変更・公開、GitHub設定変更、実USB書込みは別途承認を要する。配布確定済みMI68 PDFと展示用A4紙は変更しない。

## 18. 実装時に確定する事項

| 項目 | 確定する時点 |
|---|---|
| 起動プロファイル・必須／任意サービス・Ready位置・時間源 | Aの実装前～実装中 |
| 公開操作、エラー、バッファ所有権、上限、必要機能の表現 | Bの仕様・雛形 |
| 公開型の定義元、C／Rust名、版・互換性の規則 | Bの整合検査前 |
| 第12節のABI案、全offset、採番とエラー台帳、候補リビジョン | Bの仕様・整合試験 |
| ELF形式、NOTE、配置、CPU／浮動小数点条件、crt0 | Cのロード実装前。第12.10節の台帳で固定 |
| SYSCALL／IRETQ案、レジスター・復帰・カーネルスタック | Bで設計、Cの権限移行実装前に確定 |
| 割り込み再入、I/O待機・通知・取消し、同期／async wrapper | DのI/O公開前 |
| C標準ライブラリ、allocator、IDE／runner、SDK配布範囲 | 各SDK成果物を利用可能と案内する前 |

未確定事項を架空の既存機能やコマンドとして提示しない。小さい実装を選んで理由を残す。本書の第12節は具体的なABI候補を含むが、正式なバイナリー互換性は整合・実行試験とともに固定する。
