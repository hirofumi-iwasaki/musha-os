根拠文書: [docs/release-scope-0.3.0.md](../release-scope-0.3.0.md)。
本書は開発順序の2（stream経由のELF読込み）と3（`log` の画面出力、終了・障害の表示）を一つの工程として依頼する。
役割分担: 実装・ビルド・QEMU・証拠記録・commitはAstra、scope文書との照合レビューと文書整合はClaude、承認と実機は所有者。

## 0. 現状の認識（レビュー側で確認済み）

- `05c8d97` でA/B/C1/C2に加え **C3（lifecycle: ロールバック・反復起動・OS復帰）** がpush済み。
- 作業ツリーには開発順序2の作業が **未コミット** で進行中: `api/src/bootfile.rs`、`api/tests/bootfile.rs`、`boot/src/external.rs`、`tools/smoke-external-elf.py`、feature `external-elf-probe`。
- 既に下された設計判断（文書化が必要）:
  - ファイル名 `MUSHA.ELF`、ルート直下、同名重複は拒否。
  - サイズ 64 byte〜16 MiB（`IMAGE_LIMIT` と一致）。
  - 読出し期限 5000 ms。
  - 16 MiB のCPU所有staging buffer（static）へ全量を読み、USBセッション終了（DMA停止確認）後に `ring3::run` へ渡す一回限り実行。
  - 拒否理由は既に `framebuffer.text` で画面表示。
  - `external-elf-probe` は `file-viewer-probe`（debug出力あり）に依存し、通常版には未統合。

これらは scope の境界内であり、方向は承認する。以下はこの延長で完成させる内容。

## 1. 完了条件（scope の必須目標との対応）

| scope項目 | この工程で満たす状態 |
|---|---|
| 外部ELFの読込み | 通常版（feature指定なし）で、データ媒体ルートの `MUSHA.ELF` を読み、C2検査を経て実行する。不在なら従来ビューアー。大きすぎる・重複・期限超過・読出し失敗・不正ELFは理由を画面表示して停止 |
| 画面出力 | `log` の内容をカーネルのテキスト描画で画面に表示する。シリアル・debugポートに依存しない |
| 終了と障害 | `exit` は結果コードを画面表示して停止。CPL3例外は既存の診断表示（vector・error code）で停止。既存のDMA停止前再利用禁止を維持 |
| 既定動作 | `MUSHA.ELF` 不在時の一覧・表示・戻るのピクセル回帰が変更なしで合格。通常版のdebugバイト出力ゼロを維持 |

C3のOS復帰は **この工程では通常版に入れない**。`exit`・障害後は停止のままとする（scopeの境界どおり）。C3はopt-inのまま維持し、回帰試験の対象に含める。

## 2. 作業内容

### 2a. 外部ELF読込みの仕上げ（進行中の作業の完成）

1. 読込み中の画面状態を定義する。現在は `Files` イベント中にビューアーの `app.files` を呼ばないため、読込み中の画面が未定義。`MUSHA.ELF` 検出〜読込み完了まで、固定の案内（例: `Loading MUSHA.ELF ... <bytes>/<total>`）を表示する。進捗表示は任意、少なくとも「読込み中」と分かること。
2. 期限と実効スループットを測る。streamは1要求4 KiB・毎回chain検証のため、16 MiBを5 sで読めるとは限らない。QEMUで 16 KiB / 1 MiB / 16 MiB の読出し時間を測り、(a) 期限を実測に基づき見直す、または (b) 期限内に読める実用上限を文書に明記する、のいずれかを採る。Hello ELF（数十KiB以下）が余裕で通ることは必須。
3. 16 MiB staticの扱いを確認する。EFIファイルサイズに含まれないこと（BSS）、UEFIローダーが確保する実メモリ量、既存のarena・診断RAM検査との競合がないことを確認し、文書に記す。
4. 読込み途中の媒体取外し・取消しは既存のcancel/disconnect契約に従い、`Rejected(Stream|Interrupted)` の画面表示で停止する。未確認DMA停止（`QUIESCE FAILED`）後はarenaを使わない現在の扱いを維持する。
5. 検査の順序: `Plan::parse` によるELF/NOTE検査は、可能ならUSBセッション終了前（staging完了直後）に行い、不正ELFの場合は機器を止める前に理由を表示してもよい。順序を変えない場合はその理由を記す。

### 2b. `log` の画面出力と終了・障害表示

1. カーネル側に有界のテキスト出力領域（コンソール）を用意する。仕様は実装選択だが、次を満たす:
   - 固定の矩形領域（ビューアーと同じ画面を使ってよい）。行折返し、行数上限、上限到達時はスクロールまたは最古行の破棄。
   - 入力はC2どおり所有alias経由でコピー済みの最大4096 byte UTF-8。表示はASCIIの印字可能文字と改行のみ解釈し、それ以外はビューアーと同じ代替文字で表示する。制御文字（改行以外）は代替文字。
   - 描画はカーネル所有。framebufferやレジスターをアプリへ公開しない。ABIには影響しない（`log` の戻り値・上限・権限はC2のまま）。
2. `exit`: `MUSHA.ELF exited: status <n>` の形で表示して停止。0以外も同様に表示する（試験では非0をエラー扱いにしない）。
3. CPL3例外: 既存の診断表示（vector、error code、RIP/RSP）に `MUSHA.ELF faulted` を加えて停止。カーネル側例外は従来の致命的停止のまま。
4. `log` の出力先がQEMU debugポートにも残る場合は `qemu-debug` 配下に限定し、通常版ではdebugバイトを出さない。

### 2c. 通常版への統合とfeature整理

1. 通常版（default features）に外部ELF経路を含める。`external-elf-probe` の `file-viewer-probe` 依存を外し、debug出力は `qemu-debug` 配下へ分離する。C1/C2/C3の試験構成（`ring3-probe` 系）は従来どおりopt-inのまま。
2. 通常版のビルドで `ring3-probe` 用の試験コード（固定asm payload、埋込みELF、lifecycle）がリンクされないことを確認する。
3. 相互排他のassert（embedded と external）は維持する。

## 6. 報告形式

区切りごとに次を報告する。

1. scope必須目標ごとの状態: **未着手／実装済み／QEMUで検証／実機で検証** のいずれかと、証拠ファイルのパス（`out/.../report.json`、`host-tests.log`、`result.json`）。
2. 実装中に決めた値・仕様（名前、上限、期限、領域サイズ、表示文言）と、その根拠。
3. 合格しなかった試験、再試験した経緯、未解決事項。合格に数えない。
4. scope の除外項目に触れた変更があれば明示（なければ「なし」）。
5. 通常版EFIのSHA-256と、ピクセル回帰の参照元。

## 7. やらないこと

- Rust guestの実行、Rust SDKの梱包。
- `query`/`log`/`exit` 以外のsyscall追加、ABI値の変更。
- `exit`・障害後のOS復帰を通常版へ入れること（C3はopt-inのまま）。
- ランチャー・ファイル選択UI、複数アプリ。
- 既存ビューアーの挙動変更、公開済みv0.2.0配布物の変更。
- ホスト・QEMU結果を実機結果として書くこと。
