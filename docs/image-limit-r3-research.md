# IMAGE_LIMIT and loading strategy / IMAGE_LIMIT・読込み方式 — r3 research

Status: proposal/research only (2026-10-16), source HEAD `69e5f0ca6bb88f3dc314652d59ccf7c6c2b4ffa4` plus the existing working tree. No limits, ABI, loader, allocation or USB code changed. Related owner rule: [size budget §rule4](size-budget.md); long-term [MushaMAME scenario](scenario-mame.md) follows SDL2 and precedes softpipe, not a v0.5 runtime commitment.

## English

**A constant-only increase is not viable.** [ABI schema](../sdk/abi/experimental.json) currently uses IMAGE_BASE=4MiB, IMAGE_LIMIT=16MiB, ARENA_BASE=256MiB, ARENA_LIMIT=64MiB, START_BASE=512MiB and STACK_TOP=1792MiB. [ELF validation](../memory/src/elf.rs#L53) uses IMAGE_LIMIT for both total file length and the allowed segment virtual window. [Boot reader](../api/src/bootfile.rs#L5) independently caps files at16MiB and5s, reads at most4096B per step; [external staging](../boot/src/external.rs#L5) is a real static `[u8;MAX_BYTES]`, with a compile-time equality assertion against IMAGE_LIMIT. Changing only one constant fails that assertion; changing both to256MiB adds240MiB static zero-fill RAM, not240MiB necessarily on disk, and violates the required non-static allocation redesign in size-budget rule4.

| Exact constraint / calculation | Consequence |
|---|---|
| Proposed image window `[0x00400000,0x10400000)` = `[4,260)`MiB; guest arena starts `0x10000000` =256MiB | Allowed windows overlap `[256,260)`MiB =4MiB.252MiB is only the arithmetic image limit before this adjacent arena, not an approved capacity. Actual segments may be smaller; raising the cap does not make every ELF collide. |
| Kernel backing arena [selection/clamp](../boot/src/memory.rs#L509) is chosen16–64MiB, then restricted to physical identity addresses `[32,256)`MiB (post-clamp minimum1MiB) | User segments extending into the actual backing identity mappings may fail [vacancy checks](../boot/src/ring3/elf.rs#L54) before reaching256MiB. Repositioning only the guest arena does not solve supervisor backing/kernel-image/MMIO collisions. |
| [Backing requirement](../memory/src/elf.rs#L192): sum of page-rounded PT_LOAD **memory** extents + guest arena + stack +4KiB start record; [loader](../boot/src/ring3/elf.rs#L45) also reserves20 pages (80KiB) | File size, virtual span, zero-fill/BSS and live backing are distinct. A larger cap alone cannot fit such backing in the current≤64MiB pool. Full-file staging and loaded backing coexist. |
| [Current page builder](../boot/src/memory.rs#L30) uses4KiB leaves:256MiB contiguous image =65,536 leaves,128 leaf-PT pages =512KiB, excluding ancestors/other mappings | The [256-page shared table allocation](../boot/src/main.rs#L450) is not128 fresh pages per image. Kernel/staging/backing aliases, guest arena and devices consume it too. [Rollback snapshot](../boot/src/memory.rs#L758) also fixes256 pages; resizing tables needs lifecycle/rollback/quarantine design. |
| `64×1024² / (500×1024)` = **131.072s** (2min11.072s), at a hypothetical sustained500KiB/s, before other overhead | The present5s total-read deadline rejects this workload;16MiB also takes32.768s at that rate. Neither is a measured machine speed or a proposed accepted timeout. |

| Loading option | Benefits / required redesign |
|---|---|
| Full file before launch, dynamic staging | Preserves complete bounded validation and simplest execution failure boundary; peak includes staging + copied segment backing. Reserve owned pages from a validated OS allocator or explicitly budgeted pre-EBS pool; metadata-length admission, zeroing, bounds, release/retention and load deadline must be designed. No firmware AllocatePages after EBS, no giant replacement static array. |
| Eager PT_LOAD/NOTE ranges only | Avoids storing irrelevant file bytes and can load into final non-executable backing, then finalize permissions after validation. Current Plan::parse needs a complete file slice, so split planning from reads; retain bounded header/NOTE/range validation and overlap/short-read checks and a loader interface beyond today's sequential `Files::read` (no public seek/read-at). Skipping holes may still cost I/O; BSS must be zeroed. |
| On-demand pages after launch | Potentially lower initial I/O, but requires a pager, bounded page-fault servicing, stable file/service generation, eviction/ownership and reentrancy rules. [Current external lifecycle](../boot/src/external.rs#L190) scopes USB callbacks and [recovery](../boot/src/ring3/lifecycle.rs#L62) detaches/stops before rollback/reuse. A retained raw handle/pointer cannot outlive those sessions, and a fault handler cannot assume USB can be polled recursively. This is a larger runtime change, not an existing capability. |

The primary [ELF program-header specification](https://gabi.xinuos.com/elf/07-pheader.html) distinguishes p_filesz from p_memsz and zero-filled excess; it does not select a Musha loading policy. An r3 candidate should separate file-size, virtual-image and physical-backing budgets, relocate non-overlapping windows/aliases, introduce dynamic ownership and version its NOTE/capabilities before raising limits. Update schema → generated C/Rust constants, loader/checker, linker/SDK samples, start/query reporting and tests together. Current [NOTE dispatch](../memory/src/elf.rs#L140) accepts only r1/minor1 or r2/minor2 with revision-specific features/permissions; no r3 negotiation or version-specific image-limit table exists. Preserve0.3/r1 and0.4/r2 ranges/limits and rejection behavior explicitly rather than replacing shared constants and assuming backward compatibility. libc/C++/allocator, timing, cooperative threading and SDL2 remain additional MushaMAME prerequisites, independent of increasing this limit.

## 日本語

**定数だけの拡大案では成立しません。** 現状はIMAGE_BASE4MiB、IMAGE_LIMIT16MiB、ARENA_BASE256MiB、ARENA_LIMIT64MiBです。IMAGE_LIMITはELF全file長とsegment仮想範囲を制限し、別にboot readerの16MiB/5秒/1step4096B制限があります。external stagingは実在する16MiB静的配列でIMAGE_LIMITとの一致assertがあるため、片方だけの変更はcompile失敗、両方を256MiBにすると静的RAMが240MiB増えます。ディスク増加とは別で、size-budget規則4の非静的確保設計を先に満たす必要があります。

4＋256＝260MiBなので仮想image `[4,260)` とarena開始256MiBは4MiB重なります。隣接計算だけなら上限252MiBですが採用値ではありません。実segmentが小さければ全ELFが衝突する意味でもありません。さらにkernel backingは実際のidentity mappingを32〜256MiB内に置くため、それより手前でvacancy検査に失敗し得ます。file長、仮想span、p_memsz/BSS、物理backing、同時生存するstagingを別に予算化し、guest arenaだけ動かして解決扱いにしません。

256MiB imageの4KiB leafは65,536、末端PT128page＝512KiBですが、現在のtable pool全体は256pageでkernel/backing/他mappingと共用し、rollback snapshotも256page固定です。単なる容量増では足りず復帰・停止・quarantineの設計が要ります。仮定500KiB/sで64MiBは **131.072秒**、16MiBでも32.768秒で、現5秒deadlineでは読めません。実測性能・新timeoutの採用ではありません。

上表の比較どおり、全読＋動的stagingは検証境界が単純な反面peak RAMが大きく、必要長に応じた所有page確保・zeroing・release/保持が必要です。segment/NOTEだけの先行読込みは不要file部分を減らせますが、header/範囲検証、短読、BSS zeroと新しいrange読取り境界が要り、現Filesには公開seek/read-atがありません。on-demandはpager/例外処理・USB session世代・所有権・再入の大きな変更です。停止・callback復帰・rollback後にraw handleを残したり、page fault中にUSBを再帰pollできると仮定したりしません。EBS後のfirmware確保や巨大静的配列への置換は案にしません。

r3候補ではfile/仮想/物理上限、衝突しない配置とalias、動的所有権、NOTE/capabilityを設計し、schema・生成C/Rust・SDK/linker/checker・loader/query/testsを揃えます。現実装はr1/minor1とr2/minor2だけを受理しr3交渉はありません。0.3/r1、0.4/r2の既存制限と拒否挙動を版別に保持し、共有定数の置換だけで互換とはしません。MAMEはSDL2の後、softpipeの前という長期順序で、libc/C++/本物のallocator・時刻/thread等も別条件です。本書は採用決定でも0.5実装追加でもありません。計算と参照source hashは `out/image-limit-research/arithmetic.json` に保存しました。
