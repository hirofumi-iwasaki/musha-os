## English

At clean source commit `d1692a8f641ab1c3cd4982f66e94ea5cd9c54e9f`, the two local normal builds agree byte for byte, while the passed CI run `39424403015` produces a different EFI. The local and CI EFI images are both 850,432 bytes. Their SHA-256 values are `b246620ed313151c8f1cd5ff3f219d31454b29acc58e7aea2e594533fabe5a87` and `cc87ecf8e61c009c4c4b09a72e61b320cb5f1b320eb07a10c282513c1fb3e305`, respectively. The PE `.text` virtual sizes are 646,342 and 646,406 bytes; `.rdata` virtual sizes are 41,360 and 41,364 bytes. The comparison found 37,697 changed bytes in the padded `.text` region and 435 in `.rdata`; the initialized `.data` bytes agree. This rules out a difference confined to PE timestamps or debug metadata.

The normal EFI includes lwIP C objects compiled by `boot/build.rs`. CI explicitly sets `CC` to Homebrew Clang 23.1.0, while the local build uses Apple Clang 21.0.0. The Rust compiler and its LLVM version are identical in both manifests. As a source-level check, compiling the 19 lwIP translation units plus two port C files with the local Clang settings and comparing 24-byte instruction windows against the two PE `.text` sections found, for example, 241 local versus 43 CI matches from `inet_chksum.c`, 560 versus 93 from `dhcp.c`, and 185 versus 63 from `net/port/compat.c`. Relocations, dead-code removal, and common instruction sequences prevent those counts from being a proof by themselves, but they connect the differing executable section to the C compilation path. The exact contribution of compiler optimization and linker layout cannot be separated without building both versions of Clang against the same source or retaining CI object files. The immediate reproducibility action is to pin `CC` to one compiler build in both environments and compare full EFI outputs; neither the current local agreement nor the CI pass proves cross-environment byte identity.

The FAT writer already snapshots all touched metadata sectors and, after a failed metadata write or final sync, attempts reverse-order rollback including the failed sector. This change adds a bounded readback of every sector in that rollback set after its sync. It reports ordinary I/O failure only when the old bytes were actually read back unchanged; failed readback or differing bytes report `RecoveryRequired`. Host tests cover a recoverable write that partially changed the backup FAT sector and was restored, a device that acknowledges rollback but stores different bytes, and a sector that becomes unreadable. The focused writer suite passed 12 tests. A normal QEMU create/overwrite case finished with `fsck_msdos -n` status 0.

The intentional 4,096-byte-sector QEMU interruption still sends only 1,024 bytes of the first FSInfo WRITE(10) packet. The BOT command remains pending, so new rollback writes cannot safely use its DMA buffers. The QEMU result remains `RecoveryRequired`; both FAT copies and payload changed, while FSInfo and the directory stayed old, and `fsck_msdos -n` remains 0 before versus 206 after. Goal 4's clean-checker condition is **not met** for this case. This patch makes recoverable rollback verifiable; it does not claim power-loss atomicity or recovery when the medium disappears.

To recover the interrupted BOT case within the OS, the next design must stop the affected xHCI bulk endpoint transfers and prove that the old transfer descriptors can no longer access their DMA buffers. An in-place path would then issue the BOT Mass Storage Reset class request on endpoint zero, clear halt on both bulk endpoints, and reset or reconfigure the xHCI endpoint dequeue state before using a new BOT command. If endpoint retirement cannot be proved, the alternative is a full controller halt with PCI bus mastering disabled, followed by a fresh controller/device setup; endpoint-zero requests cannot run while the controller is halted. Either route must re-identify the same medium and confirm write-through before replaying the saved metadata sectors. Every restored sector must be read back and the filesystem checker must be clean on the disposable QEMU image. The current storage path has no BOT reset, endpoint clear-halt, or xHCI endpoint dequeue recovery primitive. Required negative tests include disappearance during reset, reset/control failure, stale completion events, silent write corruption, and failure to re-identify the same medium. Until that transport sequence is implemented and tested, the pending-command path must preserve `RecoveryRequired` and the DMA-stop-before-reuse boundary.

Evidence: `/private/tmp/musha-040-preflight-20261022/` contains both EFI files and manifests; `/private/tmp/musha-efi-fat-qemu-partial-20261022/` and `/private/tmp/musha-efi-fat-qemu-create-20261022/` contain QEMU logs, images, checker results, and result JSON. These are disposable local tests, not hardware acceptance. No physical USB was written.

## Follow-up: same compiler and bounded BOT recovery

An isolated build of the same clean commit with the exact Homebrew Clang 23.1.0 used by CI produced an EFI byte-identical to CI run `39424403015`: 850,432 bytes, SHA-256 `cc87ecf8e61c009c4c4b09a72e61b320eb07a10c282513c1fb3e305`. The Apple Clang 21.0.0 build remains different (`b246620ed313151c8f1cd5ff3f219d31454b29acc58e7aea2e594533fabe5a87`). With source, Rust toolchain, and build arguments held fixed, the C compiler choice accounts for the observed EFI difference. The verified compiler bottle and exact commands are recorded in `/private/tmp/musha-040-preflight-20261022/same-clang-result.json`. No CI run was dispatched.

The QEMU partial-metadata probe now retires both xHCI bulk endpoints before reusing BOT DMA, issues the class BOT reset over endpoint zero, clears both endpoint halts, sets both xHCI dequeue pointers, and checks the USB device descriptor, capacity, first and last sector fingerprints, root-port connection state, and write-through caching again. Only then does the FAT writer replay and read back its saved metadata. On the fresh 4,096-byte-sector image, the same one-packet FSInfo interruption returned `Err(Io(Io))` after verified rollback: only the unallocated payload sector changed, all five metadata snapshots matched their old bytes, and `fsck_msdos -n` returned 0 both before and after. Evidence: `/private/tmp/musha-bot-recovery-qemu5-20261022/result.json` and its debug log.

The production pairing writer has a separate strict recovery path for failures after an xHCI TD is already retired. It requires the xHCI forced Stop Transfer Event for each endpoint, its correlated Stop command completion, and an output endpoint context in Stopped state before resetting BOT. An active or uncertain TD, a failed reset or control transfer, disconnection, an identity mismatch, or failed cache confirmation blocks rollback writes and results in `RecoveryRequired`. Recovery is attempted at most once per save. QEMU omits the specification-required forced event for an empty ring; the QEMU injection path alone accepts a successful Stop command plus Stopped output context in that case. This emulator exception does **not** validate the strict production event gate or physical hardware behavior. The relevant protocol requirements are [xHCI 1.2b, section 4.6.9](https://cdrdv2-public.intel.com/625472/625472_xHCI_Rev1_2b.pdf) and [USB Mass Storage Bulk-Only Transport, section 5.3.4](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf).

Disposable QEMU fault cases for Stop failure, BOT reset failure, and media identity mismatch each stayed `RecoveryRequired`; the checker returned 206 after the intentionally unrecovered interruption. Their reports are `/private/tmp/musha-bot-recovery-{stop,reset,identity}-20261022/result.json`. Host tests cover exact, missing, mismatched and duplicate forced-event correlation, plus unrelated input events, and the filesystem writer's rollback readback. This is bounded in-session recovery, not a persistent journal or a power-loss guarantee.

Validation after the change: 77 `musha-fs` tests and 71 `musha-xhci` tests passed; the normal 4,096-byte QEMU create/overwrite case remained checker-clean (`/private/tmp/musha-bot-recovery-create-20261022/result.json`); the four-case offline regression passed its split-input, stop-failure quarantine, partial-metadata, and LAN-disabled cases (`/private/tmp/musha-bot-offline-regression-escalated-20261022/timings.json`).

## 追記: 同一 Clang と有限の BOT 復旧

CI と同じ Homebrew Clang 23.1.0 を隔離環境で使い、同じ clean commit をビルドすると、CI run `39424403015` の EFI と 850,432 byte 全体が一致した。SHA-256 は `cc87ecf8e61c009c4c4b09a72e61b320eb07a10c282513c1fb3e305`。Apple Clang 21.0.0 の EFI は異なる。ソース、Rust toolchain、ビルド引数を固定した比較で、観測した EFI 差の原因は C compiler の選択と確認できた。検証済み bottle と実行引数は `/private/tmp/musha-040-preflight-20261022/same-clang-result.json` に記録した。新しい CI 実行はしていない。

QEMU の metadata 部分転送では、両 xHCI bulk endpoint の停止を確認してから BOT の DMA 領域を再利用する。endpoint zero で BOT reset、両 endpoint の halt 解除、xHCI dequeue 設定を行い、USB descriptor、容量、先頭と末尾の sector fingerprint、root port の接続、write-through を再確認する。その後、退避した FAT metadata を書き戻して読み返す。4096 byte/sector の新しい使い捨て画像では、FSInfo の1 packet中断後に検証済み rollback を経て `Err(Io(Io))` となった。変更は未割当 payload sector だけで、metadata 5 sector は元の byte と一致し、`fsck_msdos -n` は前後とも status 0。証拠は `/private/tmp/musha-bot-recovery-qemu5-20261022/result.json` と debug log にある。

通常の pairing 保存経路は別の厳格な復旧処理を使う。xHCI TD の完了が確認済みの場合だけ対象とし、両 endpoint それぞれの強制 Stop Transfer Event、対応する Stop command 完了、Stopped 状態の output endpoint context を要求する。転送が実行中または不明、reset や control request の失敗、切断、媒体識別の不一致、cache 確認失敗なら rollback 書込みを止めて `RecoveryRequired` とする。保存1回につき復旧試行は最大1回。QEMU は空の ring に対して仕様上必要な強制 event を出さないため、QEMU の注入経路に限り、Stop command 成功と output context の Stopped 状態で進む。この例外は通常経路の厳格な event 確認や実機の動作を検証しない。根拠は上記の xHCI 1.2b §4.6.9 と USB BOT §5.3.4。

使い捨て QEMU 画像で Stop 失敗、BOT reset 失敗、媒体識別不一致を注入した3件は、いずれも `RecoveryRequired` を維持し、未復旧状態の checker status は206だった。結果は `/private/tmp/musha-bot-recovery-{stop,reset,identity}-20261022/result.json`。host test は強制 event の正確な一致、欠落、不一致、重複、無関係な入力 event と、FAT writer の rollback 読戻しを確認する。これは稼働中セッション内の有限な復旧であり、永続 journal や停電時の原子性は保証しない。

変更後は `musha-fs` の77 test、`musha-xhci` の71 test が合格した。通常の4096 byte QEMU新規作成・上書きも checker status 0を維持した（`/private/tmp/musha-bot-recovery-create-20261022/result.json`）。4件のoffline regressionは、分離input、Stop失敗時の隔離、metadata部分転送、LAN無効化の各caseで合格した（`/private/tmp/musha-bot-offline-regression-escalated-20261022/timings.json`）。
