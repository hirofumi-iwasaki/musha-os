# Bluetooth firmware loading research / Bluetooth firmware 読込み調査

Status: **research and proposal only**, 2026-10-17. No loader, bundled firmware, hardware acceptance or redistribution approval. Related: [third-party policy](third-party.md), [security policy](security-policy.md), [device support](device-support.md).

## English

**Verified facts.** Intel8265/9260/AX200/AX201 are investigation targets, not a single interchangeable firmware family. Linux v6.12 [btintel](https://github.com/torvalds/linux/blob/v6.12/drivers/bluetooth/btintel.c) distinguishes bootloader from operational firmware; it selects `intel/ibt-<variant>-<device-revision>.sfi` or `ibt-<variant>-<hardware-revision>-<firmware-revision>.sfi` from controller responses. Secure download requires acknowledged fragments, completion and boot/reset into operational firmware; matching `.ddc` configuration follows. This setup permits missing DDC. Product names alone do not establish the exact filename; `ibt-12-16`, `ibt-18-16-1`, `ibt-20-1-3` and `ibt-19-0-4` are published stems, not a verified mapping for the owner's four adapters. Capture USB ID, hardware/firmware version and boot state first. The separate legacy-ROM `.bseq` path can continue without a patch; this does **not** prove a blanket “7265 ROM fallback” for every revision or Musha-OS.

Linux [btrtl](https://github.com/torvalds/linux/blob/v6.12/drivers/bluetooth/btrtl.c) distinguishes RTL8761B UART from RTL8761BU USB using version/transport information. Published pairs are `rtl_bt/rtl8761b_{fw,config}.bin` and `rtl8761bu_{fw,config}.bin`. It selects a ROM-specific patch, combines configuration where present, transfers numbered HCI vendor-command fragments and rereads version. Both entries mark config optional; filenames do not justify cross-flashing. “All BT5 devices need downloads” is unsupported. Nor is “BCM needs no firmware”: [btbcm](https://github.com/torvalds/linux/blob/v6.12/drivers/bluetooth/btbcm.c) has model/USB-ID/board-specific `.hcd` patch paths. None proves compatibility of an unmeasured dongle.

**Acquisition and terms.** Obtain the exact vendor-authorized files or a pinned [linux-firmware](https://gitlab.com/kernel-firmware/linux-firmware) revision; retain its [WHENCE](https://kernel.googlesource.com/pub/scm/linux/kernel/git/firmware/linux-firmware/+/refs/heads/main/WHENCE) mapping. Intel Bluetooth uses [LICENCE.ibt_firmware](https://kernel.googlesource.com/pub/scm/linux/kernel/git/firmware/linux-firmware/+/refs/heads/main/LICENCE.ibt_firmware), not the Wi-Fi licence. Realtek uses [LICENCE.rtlwifi_firmware.txt](https://kernel.googlesource.com/pub/scm/linux/kernel/git/firmware/linux-firmware.git/+/a995331c96f926ba25acfc8e0c784cc0141c1e45/LICENCE.rtlwifi_firmware.txt). These permit unmodified binary redistribution subject to notices, endorsement restrictions, reverse-engineering restrictions and limited patent terms; they are not the GPL driver licence. **Owner policy remains no redistribution**: no blobs in source, EFI or release assets. No GPL implementation was copied or translated.

**Proposal, not implemented.** Current [FAT32 reader](../fs/src/lib.rs) `read_root` accepts only root 8.3 names, skips directories/LFN, uses a caller-sized buffer and at most1024 block reads. Thus `/FIRMWARE/intel/…` is a future directory-reader proposal, not a working location. An initial root `BTFW.BIN` + optional `BTCFG.BIN` could use a separate bounded manifest binding original filename, exact controller identity, source revision, byte size and SHA-256; renaming alone must never select a device. Candidate limits: firmware1MiB, config64KiB, total2MiB, checked before allocation, subject to corpus/reader-budget validation: at512-byte sectors a1MiB file alone needs2048 reads, so this requires a reviewed reader-budget change; it is not currently loadable under the1024-read cap. Stage all required bytes/hash before USB teardown; identify→validate→vendor download/ACK→operational recheck→config→ordinary HCI setup. Keep deadlines and DMA quarantine on failure. Show selected identity/name, size and SHA-256 summaries in Devices; reserve per-fragment progress and detailed stage/error records for Trace. Hash is provenance, not authentication. No generic automatic fallback. Cold-power-loss, timeout/reconnect and actual radio tests remain required.

## 日本語

**確認事項。** Intel8265/9260/AX200/AX201 は調査対象で、同じ firmware を共用できるという意味ではありません。上記 Linux v6.12 btintel は bootloader/稼働状態を区別し、controller 応答の variant・device/hardware/firmware revision から SFI 名を選択します。fragment の応答と完了、稼働 firmware への boot/reset 後に対応 DDC を適用し、この経路では DDC 欠落を許容します。上記4つの公開 stem は所有機4台への対応を確認した表ではありません。USB ID・version・起動状態の採取が先です。別の legacy-ROM BSEQ 経路には patch 不在で続行する処理がありますが、「7265 全 revision が ROM fallback 可能」や Musha-OS での成功は示しません。

Realtek は version と接続方式で 8761B UART / 8761BU USB を分け、上記 fw/config pair を使用します。ROM に合う patch と存在する config を組み合わせ、番号付き vendor HCI command で転送し version を再確認します。両 entry の config は任意ですが、B/BU の相互流用を許す根拠ではありません。「BT5 全機種で download 必須」は断定できません。BCM にも型式・USB ID・board ごとの HCD patch 経路があるため「BCM は不要」と一括りにできず、未採取 dongle の互換性は未確認です。

**入手と権利。** vendor 正規配布または revision 固定の linux-firmware から入手し、WHENCE と個別 license を保存します。Intel は Wi-Fi 用でなく `LICENCE.ibt_firmware`、Realtek は上記 license です。無改変 binary の再配布には notice・推奨表示禁止・解析禁止・限定 patent 条項等があり、GPL driver の license とは別です。所有者方針は**再配布しない**ままです。source/EFI/配布物に blob を含めず、GPL code のコピー・翻訳も行っていません。

**未実装の提案。** 現行 FAT32 は root 8.3 名のみで directory/LFN を読まず、呼出し側 buffer と最大1024 block read に制約されます。`/FIRMWARE/intel/…` は将来案です。当面の root `BTFW.BIN`/任意 `BTCFG.BIN` は、原名・厳密 identity・出典 revision・size・SHA-256 を束縛する有界 manifest と組み合わせる案に限ります。改名だけで機種選択しません。上限案は firmware1MiB/config64KiB/合計2MiB、確保前検査と実ファイル/読取り予算の検証が必要です。512byte sector の1MiBは本体だけで2048 readとなり、現1024回上限では読めません。予算変更の別審査が必要な案です。USB 停止前に全必要 byte/hash を保持し、識別→検証→vendor 転送/応答→稼働確認→config→通常 HCI の順を候補とします。期限と失敗時 DMA quarantine を保持し、Devices に identity・選択原名・size/hash の要約、Trace に fragment ごとの進捗と詳細な段階/失敗を表示。hash は真正性保証ではありません。一般化した自動 fallback は採らず、冷間起動・途中失敗/再接続・実電波試験が別途必要です。
