# Bluetooth encryption event receive diagnosis (2026-10-23)

The IMG_7820 observation is a **stored SC bond reconnect** through CSR `0a12:0001`: LE Connection Complete succeeded on handle `0048`, Start Encryption (`2019`) received Command Status `00`, and no later Encryption Change was visible before the 10-second reconnect deadline. Command Status confirms command acceptance, not encryption. The Event-IN transfer remained pending and owned. That alone does not establish a failed key, controller fault, or stuck endpoint; the ACL-IN TD position also cannot explain a missing interrupt-pipe HCI event.

The normal path arms the interrupt Event-IN TD before advancing the connection phase, polls its transfer completion via the Bluetooth mailbox or xHCI event dispatcher, copies only the completed bytes, frames them in `Stream<257>`, parses the HCI header, then dispatches `handle_event`. A completed interrupt transfer can contain a partial or multiple HCI events. The classic event mask `90 e0 04 00 00 00 00 20` enables Encryption Change v1 (`08`), Disconnection Complete (`05`), and command events; the LE mask `17 00 00 00 00 00 00 00` enables LE Connection Complete, Advertising Report, Connection Update Complete, and LTK Request. Key Refresh Complete (`30`) is not enabled, and Encryption Change v2 (`59`) is not recognized as authentication by the current state machines. Those coverage limits are observations, not established causes of the NUC5 timeout. Neither mask nor authentication policy changed in this diagnosis.

New bounded log fields at the five-second observation and terminal outcome show the mode (`stored` or `fresh`), handle, command acceptance, Event-IN/ACL completion deltas since Start Encryption, Event-IN TD arms since the request, Event-IN pending state, last transfer completion code/length, number of parsed HCI events, last parsed event code/parameter length/time, ignored-event count, and partial HCI frame progress. The trace stores no event payload, keys, nonces, IRKs, or bond records. A malformed HCI frame reports only actual/declared lengths and event code; a stream rejection reports only its error kind before the existing failure boundary. The per-connection mask lines report the configured policy once, so an advertising flood cannot consume a diagnostic event budget. Existing Encryption Change and Disconnection Complete status/handle logs identify explicit controller rejection or wrong-handle events when delivered.

Interpret the next physical trace by locating the final Event-IN line. `framed=0` with no transfer delta means the host did not observe another completed interrupt TD; it does not prove why. A transfer delta with `framed=0` suggests a partial HCI frame or empty transfer. `last-event=0f` after `2019` means only Command Status was parsed. An `08` with nonzero status or wrong handle provides an explicit rejection/identity lead. Fresh pairing instead waits for an SMP Pairing Response on ACL-IN before it reaches its later encryption wait, and should be labeled separately. Re-registration still follows [Bluetooth re-registration](bluetooth-reregistration.md): restart the OS after a stopped adapter, then use P while the pad is off before putting it in pairing mode. This work does not remove or replace any stored registration.

Host tests exercise actual HCI stream framing and the reconnect state machine (including accepted, rejected, wrong-handle and missing-event paths). The targeted `bluetooth_connection_diagnostic`, `bluetooth_reconnect`, `bluetooth_stream`, `bluetooth_security`, and `bluetooth_pairing_stages` suites passed 44 tests. The normal UEFI image built at `/private/tmp/musha-bt-target/x86_64-unknown-uefi/release/musha-boot.efi`. A `qemu-debug` normal boot with keyboard exit passed at `/private/tmp/musha-bt-qemu-debug/`; the existing Bluetooth restart and gamepad software fixtures passed at `/private/tmp/musha-bt-r2-removed/` and `/private/tmp/musha-bt-r2-gamepad/`. QEMU has no physical Bluetooth controller or peer in this regression, so it does not demonstrate that the missing Encryption Change is delivered on the NUC5.

The full `musha-platform` test suite stopped on `bluetooth_isolation::every_shared_xhci_and_clock_error_literal_is_classified`, which reports the unclassified literal `NESTED INPUT LOOP`. The same isolated test fails identically from a clean archive of HEAD `66642238aaffcf4b01fc1037ca99fdd09e6bc637` at `/private/tmp/musha-bt-head-baseline/`. This baseline failure is separate from the Bluetooth receive changes. The first featureless EFI used with `smoke-qemu.py` produced no runtime marker because that harness expects the `qemu-debug` feature; the subsequent `qemu-debug` run passed.

## 日本語

IMG_7820 の観測は CSR `0a12:0001` を使った**保存済み SC 鍵での再接続**です。LE Connection Complete は handle `0048` で成功し、Start Encryption (`2019`) は Command Status `00` で受理されましたが、10 秒の期限まで Encryption Change は見えませんでした。Command Status はコマンドの受理であり、暗号化の完了ではありません。Event-IN 転送は pending/owned のままでした。この情報だけで鍵の不一致、コントローラー故障、エンドポイント停止を断定できません。ACL-IN の TD 位置も、割込みパイプの HCI イベントが見えない理由を示しません。

通常経路は Event-IN の TD を投入し、Bluetooth mailbox または xHCI event dispatcher で転送完了を取得し、完了したバイトだけをコピーします。その後 `Stream<257>` が HCI イベントを組み立て、ヘッダー解析後に `handle_event` へ渡します。一つの転送完了には、HCI イベントの一部や複数のイベントが含まれ得ます。通常 HCI イベントマスク `90 e0 04 00 00 00 00 20` は Encryption Change v1 (`08`)、Disconnection Complete (`05`)、コマンド関連イベントを有効にしています。LE マスク `17 00 00 00 00 00 00 00` は LE Connection Complete、Advertising Report、Connection Update Complete、LTK Request を有効にしています。Key Refresh Complete (`30`) は無効で、Encryption Change v2 (`59`) は現在の認証状態機械では認識されません。これは対応範囲の確認であり、NUC5 のタイムアウト原因と確定したものではありません。今回、マスクと認証方針は変更していません。

新しい診断は暗号化待ちの 5 秒時点と終了時に、`stored` / `fresh`、handle、コマンド受理、要求以降の Event-IN/ACL 完了数、Event-IN TD 再投入数と pending 状態、最後の転送完了コードと長さ、解析済み HCI イベント数、最後のイベントコード・引数長・時刻、無視したイベント数、途中まで組み立てたフレームの長さを表示します。イベント本文、鍵、nonce、IRK、保存レコードは保持・表示しません。不正な HCI フレームは実長・宣言長・イベントコードのみ、ストリームの拒否はエラー種別のみ記録します。マスク設定は接続ごとに一度表示するため、広告イベントが診断ログの枠を消費しません。届いた Encryption Change と Disconnection Complete については、既存の status と handle の記録から明示的な拒否や handle 不一致を追えます。

次の実機ログでは、最後の Event-IN 行を確認します。転送完了の増加がなく `framed=0` なら、その後の割込み TD 完了をホストは観測していませんが、原因はまだ決まりません。転送完了が増え、`framed=0` なら空転送または HCI イベントの途中までの受信を疑い、partial 値を確認します。`2019` の後の `last-event=0f` は Command Status まで解析したことを示します。`08` に非ゼロ status や異なる handle があれば、拒否・識別の手がかりです。新規登録では、後段の暗号化待ちより先に ACL-IN 上の SMP Pairing Response を待つため、保存鍵再接続と分けて記録します。再登録は [Bluetooth 再登録手順](bluetooth-reregistration.md)に従います。アダプター停止後は OS を再起動し、パッドを切った状態で P を押してからペアリングモードにします。今回、保存済み登録の削除・置換は行っていません。

ホスト試験は実際の HCI フレーム組立てと再接続状態機械を通し、成功、拒否、handle 不一致、イベント欠落を含む対象 5 スイート計 44 件が通りました。通常 UEFI は `/private/tmp/musha-bt-target/x86_64-unknown-uefi/release/musha-boot.efi` にビルドしました。`qemu-debug` 付きの通常起動・キーボード終了は `/private/tmp/musha-bt-qemu-debug/`、既存の Bluetooth 再始動・ゲームパッドのソフトウェア試験は `/private/tmp/musha-bt-r2-removed/` と `/private/tmp/musha-bt-r2-gamepad/` で通りました。QEMU に実際の Bluetooth コントローラーや相手機器はないため、NUC5 上で Encryption Change が届くことの証明にはなりません。
